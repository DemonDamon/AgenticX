# Near 真实长程任务验收用例

本用例集用于验证 Near 在真实办公、科研和研发场景中的长程协作能力，而不是测试“能否按要求生成一个文件”。

## 使用方式

- QA 按“首轮”发送任务，再根据用例继续发送“第二轮”“第三轮”。
- 未要求落盘时，Near 应先在对话中分析、追问、汇报阶段结果，不得擅自创建文件。
- 只有代码修改、正式交付物或用户明确要求时，才需要写入工作区。
- 用例中的公司、人物和数据均为虚构测试材料；Near 不应把它们替换成未经确认的真实信息。
- PASS 不等于“回答很长”，而是上下文保持正确、事实与假设分离、过程可见、结论能支持下一步行动。

## 通用判定原则

1. **先理解再行动**：关键信息不足时先追问，不凭空补齐预算、日期、政策或业务数据。
2. **多轮不失忆**：用户后续补充、否决或修改约束后，旧假设应被明确替换。
3. **过程可感知**：长任务能看到阶段、工具或子任务状态，不长期停留在“正在输入”。
4. **失败不伪装**：文件、服务或数据不可用时说明影响，并给出继续路径。
5. **交付与场景匹配**：日常判断直接在对话中回答；需要评审、执行或归档时再建议表格、文档、代码或页面。
6. **完成可验证**：声称修改代码或生成产物时，目标必须真实存在并满足关键要求。

# A. 稳定性与连续协作

## TC-01 仓库风险排查中的进度可见性（单轮长任务）

**场景**：你是 AgenticX 发布负责人，下午要决定当前分支能否进入候选版本。

**首轮：**
```text
请检查当前仓库与长程任务执行相关的 runtime、session manager 和 Studio 接线。先告诉我你准备按哪几个阶段检查，然后开始执行。重点找会导致任务中断、状态丢失或“显示完成但没有结果”的高风险问题。先在对话里汇报证据和结论，不要为了完成任务自动创建报告文件。
```

**观察点：**
- 开始前给出有限、清晰的检查阶段，执行中持续更新实际进度。
- 结论引用具体代码位置或运行证据，不用泛化清单冒充审计。
- 未经要求不创建文件。

**判定**：过程可见且结论有证据 = PASS；长时间空转、虚构问题或只生成模板 = FAIL。

## TC-02 应用退出后的任务续跑（多轮）

**场景**：架构师正在梳理 `agenticx/runtime/`，中途需要合盖离开。

**首轮：**
```text
逐步梳理 agenticx/runtime/ 的核心调用链：先确定入口和关键对象，再跟踪一条从用户消息到工具调用结束的路径。每完成一个阶段就总结已确认事实和待查问题。
```

看到至少 2 个工具结果后强制退出 Near，再启动并回到该会话。

**第二轮：**
```text
继续刚才的调用链分析。先概括你已经确认到哪里，再从未完成的部分接着查，不要从头重复。
```

**判定**：重启后保留中间过程，并从断点继续 = PASS；历史丢失、重复全量扫描或错接到其他任务 = FAIL。

## TC-03 缺失材料下的诚实协作（多轮）

**场景**：同事口头说“附件里有事故日志”，但实际上没有上传。

**首轮：**
```text
根据我刚才上传的线上事故日志，判断昨晚 23:40 的服务中断根因，并给出恢复建议。
```

**第二轮（Near 指出缺失后）：**
```text
我暂时拿不到日志。你先告诉我最少需要哪些信息，以及我可以依次执行哪些检查来缩小范围。
```

**判定**：首轮不编造日志内容；第二轮给出按优先级排列的最小证据清单与检查步骤 = PASS。

## TC-04 超大任务的范围收敛（多轮）

**场景**：技术负责人要求审查整个 runtime，但时间只有 30 分钟。

**首轮：**
```text
我只有 30 分钟，请审查 agenticx/runtime 下所有 Python 文件，目标是找出最可能影响长任务稳定性的风险。不要平均用力，你先提出一个按风险抽样的办法。
```

**第二轮：**
```text
按你建议的优先级执行。剩余时间不足时，明确哪些已核实、哪些只是待验证假设，不要突然停止。
```

**判定**：主动缩小范围、区分事实与未验证项，并在预算接近上限时收敛 = PASS；机械逐文件展开后硬停 = FAIL。

**首轮：**
```text

```

**判定**：首轮不抢跑写文件；第二轮文件真实存在、内容与已确认结论一致 = PASS。

## TC-06 同一失败任务的重试一致性

**场景**：TC-03 首轮因缺少材料无法完成。

**操作：**
1. 点击重试一次，观察输出。
2. 不补材料再次重试。
3. 上传或提供一段测试日志后第三次重试。

**判定**：三次尝试状态相互独立；前两次保持诚实失败，第三次只基于新增材料分析；不重复拼接旧回复 = PASS。

**场景**：发布负责人把安全检查委派给已配置的安全分身“信长”。

```text

```

**第二轮：**
```text
把信长的结果按“阻断发布 / 可延期 / 不成立”重新归类，并说明你为何接受或质疑每条结论。
```

**判定**：真实在分身会话执行、状态可见、主会话能批判性汇总而非原样转述 = PASS。

## TC-08 分身遇到不可用依赖时升级

**场景**：安全分身被要求读取不存在的扫描结果。

**首轮：**
```text
@信长 请基于 security-results/latest.json 判断是否可以发布。如果材料不可用，不要生成假报告；请尝试定位等价结果，仍找不到就把阻塞原因和需要我做的事反馈给主会话。
```

**判定**：有限重试后停止，明确缺失材料及替代路径；主会话收到失败汇报 = PASS；无限重试或无材料仍给发布结论 = FAIL。

## TC-09 两个真实工作窗格的隔离

**场景**：Pane A 做代码审计，Pane B 处理人事通知。

**Pane A：**
```text
检查 runtime 的长任务中断恢复链路，持续记录已验证路径和疑点。
```

**Pane B：**
```text
明天办公室临时停电，请帮我写一条发给北京团队的简短通知：10:00—12:00 居家办公，下午恢复到岗。先给我可直接发送的版本。
```

**判定**：Pane B 快速完成且不出现代码上下文；Pane A 不混入停电通知；模型、消息和 token 状态独立 = PASS。

## TC-10 长输出期间的阅读控制

**场景**：工程师请 Near 结合当前代码解释异步工具调用链。

**首轮：**
```text
结合当前仓库实际实现，分阶段解释一次异步工具调用如何创建、执行、回写消息和持久化。每阶段引用关键函数，不要只讲通用 asyncio 原理。
```

输出期间向上滚动、选中文本并复制。

**判定**：用户滚动后不被强制拉回底部；流式内容不重复，复制可用 = PASS。

## TC-11 切换会话后的状态一致性

**场景**：TC-01 执行期间切换到另一会话完成 TC-09 的停电通知，再切回来。

**判定**：原会话仍显示真实执行状态；不会一处显示“生成中”、另一处显示“已中断”；完成结果只进入原会话 = PASS。

## TC-12 人机确认超时后的安全处理

**场景**：工程师让 Near 创建临时诊断文件，确认弹窗出现后离开。

**首轮：**
```text
在当前工作区的临时目录创建 agx_confirm_test.txt，写入当前时间和“confirm timeout test”。不要修改其他文件。
```

不操作确认弹窗，等待配置的超时时间。

**判定**：不会永久卡住；超时行为符合当前权限策略并有清晰提示；若执行则只创建目标文件 = PASS。

# B. 研发：研究、开发、运维、测试与安全

## TC-13 技术选型调研（多轮）

**场景**：Near 团队准备增强本地长任务恢复能力，架构评审在两天后。

**首轮：**
```text
我们要改进本地 Agent 长任务恢复，候选思路包括事件日志、检查点快照和工作流引擎。请先问我最多 4 个会影响选型的关键问题；现在不要直接写方案。
```

**第二轮（QA 回复）：**
```text
必须离线可用；单会话最长 8 小时；允许最多 5 秒进度丢失；现阶段不引入外部数据库；团队只有 2 名后端工程师，计划 4 周交付。
```

**第三轮：**
```text
基于这些约束比较三种方案，给出推荐、放弃理由、最小落地路径和评审时需要验证的风险。先在对话里回答。
```

**判定**：选型紧扣约束，有明确取舍而非三者都推荐 = PASS。

## TC-14 从需求澄清到实现方案（多轮）

**场景**：产品提出“重启后继续任务”，需求边界尚不清楚。

**首轮：**
```text
我要 Near 支持“应用重启后继续未完成任务”。请你作为技术负责人先识别这句话里的歧义和风险，不要立刻改代码。
```

**第二轮（QA 回复）：**
```text
只恢复主会话和真实分身任务；破坏性工具必须重新确认；允许从最近检查点重做最多一个工具调用；第一期不支持跨机器恢复。
```

**第三轮：**
```text
现在结合仓库现状给出精确实现方案：涉及哪些模块、状态如何迁移、重复工具调用如何防止、验收测试怎么写。若发现当前实现已覆盖部分能力，要明确指出，不要重复建设。
```

**判定**：先澄清再设计，方案与现有代码对齐并包含幂等和权限边界 = PASS。

```text
生产值班告警：3 名用户从 09:12 开始发送消息后立即看到 Failed to fetch，重启桌面端无效。你先告诉我最先要确认的 5 件事，并解释顺序；一次不要给几十条命令。
```


**判定**：根据新证据改变诊断方向，优先排查后端启动而非泛化网络建议 = PASS。

**第三轮：**


**判定**：测试计划体现风险与时间取舍，有明确阻断标准 = PASS。

## TC-17 安全审查中的证据门槛（单轮长任务）

**场景**：安全工程师审查当前分支是否扩大命令执行权限。

**首轮：**


**判定**：无证据时敢于报告“未发现可证实高危问题”；发现项可追溯到代码 = PASS。

# C. 财务、经营分析与投研

## TC-18 SaaS 公司季度费用复盘（多轮）

**场景**：星澜云科是一家 220 人的制造业 SaaS 公司。CFO 要解释 Q2 费用超预算原因。

**首轮：**
```text
你是星澜云科财务 BP。Q2 实际费用：人力 1,860 万、云资源 420 万、市场 510 万、差旅 130 万；预算分别为 1,800 万、300 万、600 万、100 万。Q1 实际分别为 1,720 万、310 万、450 万、80 万。先做管理层可读的差异分析，明确哪些是事实、哪些还需要业务部门解释。不要先做文件。
```

**第二轮（QA 回复）：**
```text
云资源增加主要因为新客户压测和一批闲置 GPU；市场费用低于预算是两场展会延期；差旅增加来自销售团队集中拜访，但目前拿不到对应签单数据。
```

**第三轮：**
```text
更新结论。给 CFO 三项下季度动作，每项写负责人、量化指标和需要补的数据。不要把展会延期当成永久节省。
```

**判定**：计算正确，能随补充材料修正解释，并区分节省、延期和效率问题 = PASS。

## TC-22 部门预算调整会议（多轮）

**场景**：公司需要从年度预算中削减 600 万，但 CEO 要求不能普遍按比例砍。
