## 三、实际执行链路

任务本身是对已有 HTML 文件的一处字体/背景对比度问题进行修复，但实际链路出现了以下膨胀：

1. 多次读取同一个约 12KB 的 HTML 文件，既有完整读取，也有重复的局部读取。
2. 多次尝试编辑同一文件，编辑条件与文件当前内容没有始终保持同步。
3. 编辑失败后继续进入后续轮次，而不是立即重新读取目标片段并重新生成补丁。
4. 期间出现 3 次“运行出错，本轮未收到模型最终响应”，随后又发生 3 次人工恢复/继续执行。
5. 最终虽保留了工具结果，但没有正常生成完整的最终说明。

这使得一个局部样式修复变成了“读取—尝试编辑—失败—恢复—再次读取—再次编辑”的循环。

## 四、主要问题与证据

### 4.1 执行轮次与任务复杂度不匹配

21 次模型调用对于单文件、单样式问题明显过多。每次调用都会重新承载会话状态、任务背景、工具描述和近期结果，因此即使每次实际修改内容很少，累计输入仍会快速增长。

### 4.2 编辑失败率过高

7 次文件编辑中有 4 次失败，失败率约为 57%。已观察到的失败类型包括：

- 文件在读取后发生变化，导致基于旧快照的编辑失效。
- 指定的旧文本已经不存在，导致替换条件无法匹配。

这类错误通常不需要继续扩大上下文，只需要重新读取精确目标片段、确认当前文本，再执行一次最小补丁即可。

### 4.3 失败后的恢复策略放大了成本

运行异常后连续恢复，会再次携带大量历史上下文。若没有明确的检查点和重试上限，恢复动作会把一次局部失败变成多轮重复推理与工具调用。

### 4.4 重复传输共享执行上下文

审计记录显示，多个轮次的输入规模稳定在 2–2.7 万 token 左右，而本次任务的实际业务内容非常短。这说明累计成本主要由共享上下文、工具描述、文件结果和历史执行记录构成，而不是用户需求或最终补丁。

### 4.5 完成判定不足

任务没有在“文件修改成功 + 读取验证通过”后及时收口，也没有在多次失败后明确转入“需要重新规划”的状态。最终未生成完整交付说明，表明执行状态和用户可见结果之间缺少可靠的闭环。

## 五、工具执行效率评价

### 做得较好的地方

- 使用了文件读取和文件编辑，工具方向符合任务性质。
- 文件读取和待办更新均成功，基础工具可用性没有明显问题。
- 最终确实保留了工具执行结果，数据没有因为异常而完全丢失。

### 需要改进的地方

- 编辑前后的文件快照管理不严格，导致“旧文本不存在”和“文件已变更”两类失败。
- 缺少针对单文件小改动的短路径策略，没有尽早限制任务轮次。
- 失败重试没有区分“应重新读取”与“应停止并重新规划”两种情况。
- 缺少统一的读后写验证，因此无法尽早确认修改是否已经达到目标。
- 工具成功率、失败原因、重试次数没有在用户可见结果中形成结构化摘要。

综合判断：工具本身不是完全不准确，而是工具调用编排不够准确。正确的工具被反复调用，失败状态也没有及时触发更换执行策略。

## 七、改进建议

### P0：应优先落地

1. **为单文件小修改提供短路径**：读取目标片段后，优先生成一次最小补丁；成功后立即做一次定点读取验证。
2. **编辑失败立即刷新快照**：遇到文件变更或旧文本不匹配，不要继续复用旧内容，先重新读取目标区域。
3. **限制失败重试次数**：同一文件编辑连续失败 2 次后，停止自动循环，转为重新规划或向用户报告具体阻塞原因。
4. **设置任务级轮次预算**：简单文件修改默认限制在 5 次模型调用以内，超过预算必须输出阶段性结果和失败原因。
5. **建立完成闭环**：只有“编辑成功 + 目标片段验证通过”才标记完成；运行异常时必须明确输出未完成状态。
6. **将成本拆分记录**：分别记录输入 token、输出 token、工具结果 token、重复上下文 token和重试次数，避免只看总量无法定位原因。

### P1：建议随后落地

1. **减少完整文件重复读取**：已知目标行或片段后，后续只读取相关范围；仅在验证失败时扩大读取范围。
2. **引入编辑前置校验**：执行替换前检查旧文本是否唯一存在，并将不匹配原因直接返回给调度器。
3. **增加自动化验证器**：对 CSS 颜色、背景色和对比度做定点检查，减少依赖多轮人工判断。
4. **保留可恢复检查点**：每次成功编辑后保存文件状态摘要，异常恢复时从最近检查点继续，而不是重放整段上下文。
5. **建设工具效果指标**：至少统计成功率、失败类型、平均重试次数、单任务工具调用数和“无结果轮次”。
6. **异常收口标准化**：模型调用异常时，系统应自动生成简短状态卡，包含已完成动作、未完成动作、下一步建议和累计消耗。

1. `agenticx/studio/context_usage.py` 此前将所有 GLM 统一显示为 128K，低估了 GLM-4.7 的 200K 容量；本次已修正。
2. `ContextCompactor` 默认在历史超过 20 条消息或 48K 字符时压缩。工具调用会同时产生 assistant 与 tool 两行，因此简单任务跑到约 10 个工具轮次就可能触发摘要。这是应用自己的成本/稳定性策略，不是模型窗口限制。

第二项暂未直接放宽：提高阈值可以保留更多原始上下文，但也会增加每次 API 输入和费用，需要单独做“上下文保真 vs. 调用成本”权衡，列为 P1。

### 10.4 为什么正文会进入 reasoning

GLM-4.7 默认开启 Thinking，并支持工具调用之间的交错式思考。官方说明简单轮次可按轮传入 `thinking: {"type": "disabled"}`：[思考模式说明](https://docs.bigmodel.cn/cn/guide/capabilities/thinking-mode)。

当前链路把供应商的 `reasoning_content` 包成 `<think>...</think>`，用户可见正文只认普通 `content`。本次模型在成功 `file_edit` 后，把一段已经完全成文的交付说明继续放进 `reasoning_content`，普通正文为空；Runtime 先触发一次 reasoning-only nudge，下一次仍没有普通正文，最终进入 `tool_turn_empty_fallback`。同时，旧逻辑在 nudge 时会重复写入空 assistant 行，进一步增加下一轮上下文噪音。

同一会话更早还有一组反例：12:28:52–12:29:34 连续 4 次 `glm-4.7-flash` 成功，随后 12:29:42、12:29:49、12:29:58 连续失败。因此，当前数据不能支持“几乎所有失败都由 4.5-Air 本身造成”的绝对结论。

全量本地 usage 账本只统计成功调用：

| 模型 | 成功调用 | 涉及会话 | 成功调用 token |
|---|---:|---:|---:|
| `glm-4.5-air` | 7 | 5 | 161,366 |
| `glm-4.7` | 32 | 2 | 758,567 |
| `glm-4.7-flash` | 28 | 5 | 607,770 |

由于失败调用不会写入 usage 账本，以上数据只能证明 4.5-Air 并非完全不可用，不能用于计算各模型失败率。这也是本次补错误分类的原因。

### 11.3 4.5-Air 最小探针

为区分“模型/工具协议不可用”和“Thinking 导致普通正文为空”，执行了 3 个极小的计费探针，均限制 `max_tokens=32`：

| 请求 | 结果 | 耗时 |
|---|---|---:|
| 纯文本、默认 Thinking | 请求成功，但可见输出全部为 reasoning，无普通 `OK` | 3.55s |
| 单工具 schema、默认 Thinking | 请求成功，32 个输出 token 全部进入 reasoning，无普通正文 | 21.42s |
| 同一工具 schema、`thinking.type=disabled` | 请求成功，普通正文为 `OK`，`finish_reason=stop` | 9.98s |

这组结果证明当前 4.5-Air endpoint 与工具 schema 可用，也证明默认 Thinking 对简单短任务存在可复现的正文缺失风险。单次样本不能代表整体延迟分布，但关闭 Thinking 的该次工具探针比默认 Thinking 快约 53%。

智谱官方说明 GLM-4.5 / GLM-4.5-Air 上下文为 128K，Thinking 默认开启，并支持按请求关闭；官方也明确区分用户限流和模型/平台峰值过载，建议采用排队和退避策略：[GLM-4.5 模型说明](https://docs.bigmodel.cn/cn/guide/models/text/glm-4.5)、[思考模式说明](https://docs.bigmodel.cn/cn/guide/capabilities/thinking-mode)、[速率限制](https://docs.bigmodel.cn/cn/api/rate-limit)、[API 错误码](https://docs.bigmodel.cn/cn/faq/api-code)。

### 11.4 模型切换的旧逻辑

旧链路实际包含三个互相混淆的状态：

| 状态 | 旧行为 |
|---|---|
| 当前运行模型 | `/api/chat` 发出时已锁定，4.5-Air 不会被中途替换 |
| 选择器中的模型 | 点击后立即变为 4.7 |
| session 模型字段/运行标签 | 点击后也立即变为 4.7，造成错误归属 |

另外，排队消息只保存文本、附件和 session id，没有保存 provider/model。若用户为下一条选择 4.7 并排队，之后在它出队前再次切换模型，该消息会使用最后一次选择，而不是最初指定的 4.7。自动续跑也有同类风险。
