## 1. 背景与驱动

### 1.1 商机背景

某大型会展场馆运营方（甲方设备设施管理部门）拟建智慧设施管理系统，需求沟通会与材料显示：核心诉求为**预测性维护（红黄绿健康态/RUL）、能耗根因分析、知识案例沉淀、工单移动闭环**，且甲方技术倾向与 AGX 产品理念高度同构（Agent 自主编排、固化为 skill/MCP、训练自己的垂类模型、人在回路 PDCA）。系统边界明确：数据中台与物联底座他建，我方交付数据中台之上的平台层。

**本规划不依赖该商机是否中标成立**——以该商机为样本，验证出 AGX 产品矩阵在"设施管理"这一垂类（可泛化到园区、医院、能源、交通等一切重资产运维场景）上的通用底层缺口。

### 1.2 先例佐证

某医院 ChatBI 问数项目评估中，"语义层与指标体系"被列为独立子项单独估算（约 32 人天），即：**语义层至今每个项目单做，未沉淀为产品件**。这是缺口 G1 的直接证据。该项目与本项目（若中标）都将直接复用本规划的产出。

### 1.3 现状验证结论（已逐一核实代码）

| 假设 | 验证结果 |
|---|---|
| AGX 具备 IoT/MQTT/时序数据面 | `agenticx/` 全仓检索无实质实现；`storage` 仅 文件/Redis/PG/SQLite；`data_sources` 为拉式查询网关（AkShare/世行/IMF 等金融源），非持续接入管道 |
| AGX 具备实体语义层/资产主数据 | `knowledge`/`brain` 为文档态 RAG（GraphRAG 有图谱能力但无资产本体模型与主数据管理） |
| AGX 具备领域分析算子库 | `tools` 内置集偏通用（文档/搜索），无时序异常检测、健康评估、能耗基线等算子 |
| AGX 具备业务事件闭环引擎 | `hooks` 为进程内事件总线，无跨系统业务事件、告警收敛、工单 northbound |
| AGX 具备外部写回安全边界 | approval/residency 设计存在（OC 计划 G2 同构），但未上升为"任何写回外部系统"的通用能力 |

## 2. 定位与原则

1. **只做底层、通用、可复制**：所有缺口件不带客户私有属性，按产品矩阵件立项，商机只是第一消费者；
2. **两步走**：每个缺口先出"方案框架"（可直接进标书/售前方案），验收后再落产品化代码；
3. **不重复造轮子**：与 OC 计划 G1（runId 状态机/幂等）、G2（审批闭环/审计链）同构的部分直接复用其协议骨架，不另起炉灶；与 ECP 计划重叠的治理件（IAM/审计/网关）不重做；
4. **边界纪律**：IoT 接入面、数据中台不属于本规划（本商机中他建）；完整时序面仅作 P2 预研，为"客户需要我方全栈"的下一单做准备。

## 3. 缺口总览

| # | 缺口 | 优先级 | 一句话定义 | 预估工作量 |
|---|---|---|---|---|
| G1 | 实体语义层与资产主数据 | P0 | "区域→专业系统→设备→部件"的资产本体 + 主数据管理 + 可被 Agent 消费的语义层服务 | 方案 5-7d / 产品化 25-35d |
| G2 | 时序领域算子库 | P0 | 时序统计/异常检测/健康评估/能耗基线/RUL 冷启动算子，封装为标准 Agent tools | 方案 4-6d / 产品化 20-30d |
| G3 | 预警→工单事件闭环 | P1 | 跨系统业务事件引擎：预警收敛→通知路由→工单 northbound（幂等/重试/补偿）→案例回流 | 方案 3-4d / 产品化 15-20d |
| G4 | 外部写回安全边界 | P1 | 分析结果写回外部系统（子系统预警、第三方系统）的统一通道：审批、审计、限流、可回滚 | 方案 2-3d / 产品化 10-15d |
| G5 | 行业可视化组件 | P2 | 组态/点位/管线/层级钻取/告警落点等交互模式组件（基于 enterprise ui 扩展） | 方案 2-3d / 产品化 15-25d |

## G1 实体语义层与资产主数据

**现状证据**：knowledge/brain 是文档态 RAG；医院项目语义层单独做（32 人天）；本项目 4.5 万条设备台账 Excel 存在错别字/编码不统一，需要清洗、对齐、建模。

**目标形态**：
- 资产本体：位置（区域/建筑/楼层/空间）× 系统（专业系统/子系统）× 设备（类型/型号/厂商）× 部件 × 测点的标准模型，以 ontology schema 落库；
- 主数据管理：批量导入清洗管道（Excel/CSV → 实体对齐 → 冲突处理 → ID 体系）、增量维护 CRUD、与多源编码对齐（设备编码/资产编码/子系统点号）；
- 语义层服务：实体-关系-指标的查询接口（图谱 + 指标定义，含行业黑话词表注入机制），供垂类 Agent 与 ChatBI 类应用统一消费；
- 与 brain/GraphRAG 的关系：brain 提供检索底座，语义层提供**结构化事实底座**（二者并存，实体态补文档态）。

**交付物**：`agenticx/semantic/`（本体 schema + 主数据管道 + 查询服务）+ 售前方案模板章节。

**验收**：以本项目设备档案为基准数据集，导入后实体对齐准确率、Agent 可基于语义层回答"某设备属于哪个系统/关联哪些测点/历史告警"类问题的端到端 demo；医院问数场景回归验证。

## G2 时序领域算子库

**现状证据**：tools 内置集无时序算子；storage 无时序能力；客户历史数据不足、要求"从现在开始采"，算法必须小样本冷启动。

**目标形态**：
- 算子包（`agenticx/tools/domain_ops/` 或独立 `agx-domain-ops` 包）：基础统计、突变/掉线/ESD/变点检测、健康指标（HI）计算、红黄绿三态评估、能耗基线与偏差、根因关联分析；
- 冷启动策略：规则 + 统计基线先行，随数据积累切换至学习型模型，全程可解释（输出证据链，满足标书"可解释性"议题）；
- 标准 Agent tool 封装：统一输入输出 schema，垂类 Agent（空调/配电/电梯/给排水）挂载同一套算子底座 + 各自阈值/参数配置；
- 轻量时序缓存：平台侧对中台/物联底座数据的订阅、降采样、窗口缓存（不做完整接入面）。

**边界**：不做完整 MQTT/IoT 接入面（P2 预研）；不做控制指令下发。

**验收**：在合成 + 公开时序数据集上算子基准测试；接入真实展会/场馆样例数据的端到端分析 demo（脱敏）。

## G3 预警→工单事件闭环

**现状证据**：hooks 为进程内事件总线；评审议题 07 点名工单集成需幂等/重试/补偿。

**目标形态**：跨系统业务事件引擎——预警事件产生→告警收敛（去重/分级/抑制）→通知路由→工单 northbound 模板（对接既有工单系统 API，带幂等键/重试/补偿）→工单关闭后"预测 vs 实际"比对→案例回流 cases/knowledge。**协议骨架复用 OC 计划 G1（runId 状态机）**。

**验收**：与 mock 工单系统的集成测试（幂等/重试/补偿场景全覆盖）；从预警到案例沉淀的全链路 demo。

## G4 外部写回安全边界

**现状证据**：评审议题 02 要求分析结果回传子系统侧预警，甲方自定"首期不下发控制指令"；EGW 已有 blake2b 审计链与治理能力。

**目标形态**：统一写回通道——所有写外部系统的动作（预警回写、工单创建、第三方通知）走单一出口：审批挂起（复用 OC 计划 G2）、全链审计、限流、可回滚（补偿动作）。将 EGW 治理能力包装为标书差异化卖点（"AI 决策的安全边界"）。

**验收**：写回动作 100% 过审批+审计；红蓝演练：越权写回、重放攻击、审计篡改均可拦截/可追溯。

## G5 行业可视化组件

**目标形态**：基于 enterprise ui 扩展行业组件层：设备层级钻取、告警落点图层、点位/管线示意、组态面板；扫码入口（移动端）→ 设备档案/模型的交互模式模板。

**边界**：不做 3D/BIM 引擎（集成第三方），只做 Agent 侧的数据-视图契约。

**验收**：一个可复用的"设施总览"页面模板，配 demo 数据即可在售前环境演示。

## 4. 优先级与里程碑

| 阶段 | 内容 | 出口标准 |
|---|---|---|
| **P0（立即）** | G1+G2 的方案框架（可直接进标书技术方案章节） | 方案评审通过，售前可直接引用 |
| **P1（商机锁定后/产品窗口）** | G1 主数据管道 + G2 算子包最小可用；G3+G4 协议骨架 | 各自验收项通过 |
| **P2（产品化沉淀）** | G1 语义层服务 + G3 事件引擎 + G4 写回通道 + G5 组件；完整时序接入面预研 | 进入产品矩阵发布清单 |

依赖关系：G1 是 G2/G3/G5 的地基（实体都没有，算子和事件无从挂靠）；G3 依赖 OC-G1 状态机；G4 依赖 OC-G2 审批闭环。

## 5. 与既有规划的关系

- **OC 计划**：G1（runId/幂等）→ 本规划 G3 的协议骨架；G2（审批闭环/审计）→ 本规划 G4 的安全底座；G4/G5（设备配对/能力路由）→ 时序面 P2 预研的信任模型参考。两个规划正交：OC 做协议层，本规划做数据与领域层。
- **ECP 计划**：IAM/审计/网关治理件不重做，G4 直接消费。
- **医院问数项目**：G1 语义层验收场景之一（回归验证 32 人天口径可降为配置成本）。

## 7. 风险与开放问题

1. G1 本体的行业普适性 vs 首个客户的定制深度——先以设施管理垂类为准，预留行业 profile 扩展点；
2. G2 冷启动算法的交付承诺风险——标书中只承诺"规则+统计基线"级别的可验证能力，学习型能力写为演进路线；
3. G3 工单系统对接的接口不确定性（甲方既有系统 API 文档未拿到）——northbound 模板按适配器模式设计；
4. 本商机竞争风险——若我方不中标，本规划产出仍直接服务下一个设施/园区类商机，投入可回收。
