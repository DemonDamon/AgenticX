# AGX 企业能力平台 Master Plan

> **状态**：Accepted · 执行中（见 `2026-11-01-enterprise-capability-platform-subplans.md`）  
> **日期**：2026-11-01（Asia/Shanghai）  
> **分支目标**：合入 `main` 的平台能力（非客户交付包）  
> **原则**：只建底层通用、可复制、高价值的能力与组件；项目侧定制不进 AGX 主线；闭环用完整 case E2E 验收，不靠口头对照

---

## 1. 结论（评审请先拍这五条）

1. **主线只做平台能力**：目录 → 分发 → 租户库 → 分配 → 运行时注入。客户文案、固定审核级数、席位云盘、运营商订购同步等一律留在项目交付包。
2. **要建成什么**：可复用的 **能力货架 + 跨租户分发（含 revoke）+ 可插拔审核 + 专家包生命周期**，挂在现有 `admin-console` / `web-portal` / Desktop / Gateway 上演进，不另起「单客户后台」。
3. **专家包路线（已拍）**：**Bundle + Capability Pack 产品化** 为 `expert_package` 一等公民；不新建平行 Expert 实体；不把 Gateway wasm pack 伪装成业务专家包。
4. **Revoke 默认策略（已拍）**：revoke 后 **停止新下发与后续更新，保留租户已同步副本**；「立即从 bootstrap 剥离」仅作租户/平台可选策略，禁止隐式自动恢复历史授权。
5. **分期交付**：每期可独立演示；禁止一次做完「超管端全家桶」。粗估主线 **约 3.5～4.5 人月**（模型/Token 已覆盖，不计入）。

## 2. Main 准入闸门（硬约束）

### 允许进 `main`（`agenticx/`、`enterprise/` 通用层、Desktop 通用运行时）

- 与租户无关的数据模型与 API：平台目录、分发 grant/revoke、货架状态机、审批工作流内核、`expert_package` 与 Bundle/Pack 的产品化接线。
- 通用权限切分：平台运营角色 vs 租户 admin；对「平台下发物」只读元数据 + 二次分配。
- 通用 UI/API 壳：货架列表、发布/版本、审批队列、分配面板——**无客户品牌与业务流程硬编码**。
- 回归与 E2E fixture：用合成多租户 case 证明闭环（见 §8），fixture 不绑定真实客户配置。

### 禁止进 `main`（项目交付包 / B 包 / 客户配置）

- 云盘/网盘配额、成员容量、席位订购与运营商能开同步。
- 固定「成员→企业→平台」三级审核路径、专属角色名、专属 ZIP 表单与品牌话术。
- 某一客户的种子数据、文案、流程开关默认值、仅该客户需要的后台菜单信息架构。
- 为单项目开的 fork API、平行资产模型、或「只服务该项目」的独立后台。

### 判定口诀

> 下一个 toB 多租户项目能否 **只配租户与 grant、不改平台代码** 就复用？能 → 主线；不能 → 项目包。

## 3. 我们要建的能力（直接表述）

### A. 跨租户分发与边界（最高杠杆）

- 平台目录条目可 **grant** 给租户；企管对平台下发物 **不可改元数据**，只能做可见范围 / 二次分配。
- **revoke 默认**：停止新下发 + 停止后续更新，**保留已同步副本**；可选策略：立即从 bootstrap 剥离。
- **复用**：`tenants` / RBAC；Capability Pack assignment；Desktop bootstrap「停用不下发」。
- **新建**：平台目录项 + `tenant_distribution_grants` + revoke 事件与策略枚举；平台运营权限切分（阶段 1 可 API-first）。

### B. 统一货架生命周期

- 技能与专家包共用：`draft → published → deprecated`（可对齐策略域 draft/publish），版本号、产物引用；登记包必须过 guard/scan。
- **复用**：`enterprise_skills` + scan；`guard.py` / skill-registry；桌面 ZIP registry；策略 draft/publish。
- **新建**：包产物模型（不仅 URI 文本框）；多版本共存 + 指定生效版本（百分比灰度非本主线，除非真实项目另立）。

### C. 可插拔审核工作流

- 通用「申请单 + 1～N 级审批节点」；资源类型 skill / expert_package；动作含上架 / 安装 / 引入平台物。
- 级数与角色 **可配置**；提供「企管单级」「企管+平台」两种 **预设配置**，不是写死代码路径。
- **复用**：桌面 pending_queue；策略 publish 门禁；scan 作为自动节点（dangerous 不可人工改成 safe）。
- **新建**：申请单/步骤表；Admin 最小审批 UI + Portal 提交侧；与货架状态机钩子（未通过不得 published）。

### D. 专家包一等公民

- 业务「专家」= 带元数据的能力组合（技能 + MCP/连接器 + 可选 avatar/memory/策略），与技能共用货架、分发、审核、分配。
- **复用**：`agx-bundle.yaml` / Bundle；`enterprise_capability_packs`。
- **新建**：Catalog 类型 `expert_package`；Admin 创建/版本；Portal/Desktop 展示与安装或下发。

### 明确不做（非目标）

- 云盘席位与订购同步；重做模型服务 / Token 配额；Gateway wasm 当业务专家包；第三套 Expert-only 资产模型。

## 4. 目标架构（逻辑）

```
┌─────────────────────────────────────────────────────────┐
│  Platform Catalog（平台目录）                              │
│  skill | expert_package | …                               │
│  draft/publish/version + scan                             │
└───────────────────────┬─────────────────────────────────┘
                        │ distribute / revoke
                        ▼
┌─────────────────────────────────────────────────────────┐
│  Tenant Library（租户库）                                 │
│  平台下发（只读元数据）+ 租户自建                           │
│  assignment → Desktop bootstrap / Portal inject           │
└─────────────────────────────────────────────────────────┘
        ▲
        │ optional: apply → Approval Workflow
        │
┌─────────────────────────────────────────────────────────┐
│  Runtime：Desktop Marketplace + Enterprise sync + Portal │
└─────────────────────────────────────────────────────────┘
```

现状：`enterprise_skills` + Capability Pack ≈ 租户库 + 分配层。缺上半截平台目录与分发，以及货架/审核把两层粘起来。

## 5. 分期计划

### 阶段 0 · 对齐（约 3～5 人日）— 本修订已预填决策

- [x] 专家包：**Bundle+Pack 产品化**（唯一路线）。
- [x] Revoke 默认：**保留已同步副本 + 停止更新/新下发**；立即剥离为可选。
- [x] 阶段 1～2：**仅授权下发 + 只读元数据**；「安装副本」模式 **推迟到阶段 4**，企业策略开关，默认关。
- [x] 平台超管：阶段 1 **API-first**（Internal API + 运维/简易页）；完整超管 UI 不阻塞阶段 1。
- [ ] 评审关门后：链到 `docs/roadmap.md`（建议 M19 Enterprise Capability Platform）。
- [ ] 确认本文件准入闸门（§2）写入纪要。

### 阶段 1 · 分发语义（约 3～4 周 / ~1～1.2 人月）

**交付**：跨租户 grant/revoke 可演示；租户侧平台物只读元数据；assignment 仍走现有 Pack；**不做安装副本**。

- 数据模型与迁移；Admin 区分「平台下发 / 租户自建」；权限校验。
- 回归：revoke 后 Desktop bootstrap 与选定策略一致。
- **E2E 验收（合成 case）**：两租户 A/B；平台 grant 同一技能包仅给 A；A 可分配、B 不可见；revoke A 后 A 不再收到更新且默认仍保留已同步副本（可选策略测「立即剥离」）。

### 阶段 2 · 货架生命周期（约 2～3 周 / ~0.7～1 人月）

**交付**：技能（及专家包雏形类型位）draft/publish + 版本；包登记强制 scan。

- 状态机与 API；Admin 草稿/发布；ZIP/bundle 上传校验。
- **E2E 验收**：草稿不可被 Portal 注入；发布后可分配；切换生效版本后运行时只注入指定版本。

### 阶段 3 · 审核工作流（约 2～3 周 / ~0.7～1 人月）

**交付**：可配置 1～N 级；两个预设配置可用。

- 申请单模型 + API；与 publish/引入动作挂钩；scan 自动关卡；最小 UI。
- **E2E 验收**：两级配置下未过平台节点不能上架；驳回原因可审计。

### 阶段 4 · 专家包产品化 + 目录分层（约 3～4 周 / ~1～1.3 人月）

**交付**：`expert_package` 可上架/分发/分配；前台区分平台目录与组织库；**可选「安装副本」**（企业策略开关，默认关；与「纯授权下发」并存）。

- Bundle ↔ Catalog；Pack 作为分配视图或生成物。
- **E2E 验收（完整闭环 case）**：一个专家包 = 2 skill + 1 MCP；grant → 审核（若开）→ 租户分配 → 成员侧可见可用；revoke 行为符合阶段 0；打开「安装副本」开关时副本落点与撤销语义可测、可文档化。

### 阶段 5 · 硬化与文档（约 1 周）

- 权限矩阵、审计事件、错误码、联合发版说明。
- 对外表述：这是 **AGX 企业能力平台**；具体客户是落地验证场，不是平台唯一消费者。
- 与 `docs/roadmap.md` M18 交叉引用，避免双轨叙事。

## 7. 成功标准（主线完成时）

1. 新项目要「平台发能力给企业」：**不必开定制分叉**，只配租户与 grant。
2. 技能与专家包共用货架与审核挂点；新资源类型成本是挂枚举，不是复制后台。
3. §2 禁止项无一泄漏进 `main`；项目定制只存在于交付包。
4. 完整 E2E case（阶段 4）证明：上架 → 分发 →（可选审核）→ 分配 → 运行时可用 → revoke，问题闭环。

## 8. 闭环 E2E Case（主线验收用，非客户配置）

合成场景名称建议：`e2e-enterprise-capability-platform`。

| 步骤 | 期望 |
|---|---|
| 平台登记技能包 S 与专家包 E（2 skill + 1 MCP） | draft 不可注入 |
| 发布并 scan 通过 | 可进入目录 |
| grant 仅给租户 A | 租户 B 目录不可见 S/E |
| 租户 A 二次分配给部门 D | 仅 D 成员运行时可见 |
| （若开审核）成员申请引入 | 未批不得 published/安装 |
| revoke A（默认策略） | 停止更新；已同步副本仍在；新 bootstrap 不再拉新版本 |
| 打开「安装副本」再测一组 | 副本落点与撤销可预期（阶段 4） |

客户项目可用同一套能力做落地验证，但 **客户种子与文案不进本仓库主线**。
