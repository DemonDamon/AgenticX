# 同一个模型，五个 Harness，差距 30 个百分点：一次 Terminal-Bench 2.1 对照实验

## 引子：问题不在模型，在 Harness

过去两年，Agent 领域的评测都在问"哪个模型更强"。但真正跑过 Agent 系统的人会告诉你另一件事：**同一个模型，接上不同的 Agent Harness（执行框架），最终成绩能差出 30 个百分点。**

模型是发动机，Harness 是整辆车——传动、转向、油门响应，缺一不可。我们为此做了一次严格对照的实验，跑完了全部五个 harness，数据已经齐了。

## 实验设计：把变量摁死，只留 Harness

五个 Agent Harness，接入同一个模型、同一份数据集：

| 维度 | 设定 |
|---|---|
| 模型 | DeepSeek V4 Flash（同一 API Key） |
| 数据集 | Terminal-Bench 2.1（89 道终端环境实操题，版本 sha256 锁定） |
| 评分 | Harbor 内置确定性 verifier（跑测试脚本），无 LLM 裁判 |
| 超时 | Agent 3 倍基准超时，环境搭建 6 倍 |
| 并发与重试 | 全部 4 并发，断点续跑，报错不计入完成、自动重试 |

五个 Harness：AgenticX（自研）、dsh（DeepSeek 官方 harness）、OpenCode、Hermes、Pi。

方法上有个关键决策：**不用 LLM 当裁判**。Terminal-Bench 的题目全部有客观测试脚本，verifier 是确定性的——这消除了评测中最大的隐性偏差源（裁判模型的偏好）。

### 为什么是这五个 Harness？

市面上远不止五个 Agent 框架，入选标准是四条硬门槛：**能以 headless 模式跑进任务容器**（评测刚需，依赖交互式终端的进不来）、**通过标准 API 接入任意模型**（模型层必须可替换）、**开源或提供官方适配层**、**有真实社区使用量**（不拿玩具比）。

过筛之后，五个正好覆盖了设计光谱的两端和中间：dsh 是**模型厂商官方 harness**——厂商为自己模型调出的最佳实践，赢它才有含金量；OpenCode 是**社区主流**——终端 Agent 的事实标准之一；Hermes 代表**研究向的另一种工程哲学**；Pi 是**极简实现**——天然的地板对照组；再加上自研的 AgenticX。

先澄清一个高频误会：OpenHands 和 OpenCode 没有任何关联，名字像纯属巧合。前者是 OpenDevin 社区（All Hands AI 公司化运作）的**平台级系统**——浏览器客户端、Agent Server、沙箱控制面、事件流架构一应俱全；后者是驻在终端里的**单进程工具**（195k stars 的社区第一 CLI）。功能上重叠，架构哲学相反：一个要「替你干活的平台」，一个是「终端里的副驾驶」。

不选 OpenHands 的硬理由是形态错配：我们的评测装置要求 agent 以 headless 方式跑进每个任务容器、由适配器协议驱动——OpenCode 一个二进制扔进容器即用；OpenHands 要么在容器里反复拉起它的 server 全家桶（445 次），要么写深度适配器，两条路测出来的都是适配水平而非框架水平。此外，它的差异化能力（沙箱编排、多 agent 委派、浏览器 agent）在单终端单任务的赛制里根本不会被触发。至于其他没进场的：Claude Code 这类闭源产品与自家模型、账号体系深度绑定，接不进模型层；Aider 聚焦代码 diff 编辑，任务域与终端操作不重合。

### 为什么用中间档的 Flash，而不是 Kimi K3 或更小的模型？

模型是本实验唯一的常量，选档位就是在选**区分度**。模型太强，天花板效应——所有 harness 都逼近满分，差异被压缩在最后几道超难题上；模型太弱，地板效应——模型自身就在长程任务里死循环，什么 harness 都救不回来，测到的是模型噪声而不是框架水平。

我们拿到了一个真实的数据点：有团队反馈小米 MiMo 在长程任务上失败率极高，频繁失败重试、做着做着就进入死循环。这样的模型放进本实验，五个 harness 的成绩会一起沉底、互相黏在一起——模型层的故障直接淹没了 harness 层的信号。而 Kimi K3 这样的旗舰模型，头部压缩加成本翻倍，更适合留作后续的多模型扫描实验（Flash / K3 / MiMo × 多 harness 的矩阵）。

还有一笔不太显眼的账：445+ 个 trial、单题上下文动辄百万级 tokens，dsh 沙箱事故后我们**把整批 89 题作废从零重跑**——Flash 的价位才出得起这种「把数据扔了重跑」的决策。这不是省钱问题，是方法论问题：重跑自由本身是实验严谨性的组成部分。

一句话总结：**用中间档模型测 harness，就像用中等马力的发动机测变速箱**——F1 引擎和割草机引擎，都测不出传动的差异。

## 结果

| Harness | 通过率 | 备注 |
|---|---|---|
| **AgenticX** | **88.8%**（79/89） | 第一 |
| dsh | 83.1%（74/89） | 沙箱权限修复后重跑 |
| OpenCode | 79.8%（71/89） | |
| Hermes | 67.4%（60/89） | |
| Pi | 58.4%（52/89） | |

最终排名：AgenticX > dsh > OpenCode > Hermes > Pi，头尾差 30.4 个百分点。

几个值得展开的点：

### 1. 统计上诚实的解读

单次抽样（每题每 harness 只跑一次）下，我们做了 McNemar 配对检验：

- AgenticX vs Pi：29 胜 0 负，p < 0.0001，**显著**
- AgenticX vs Hermes：22 胜 3 负，p = 0.0002，**显著**
- AgenticX vs dsh：9 胜 3 负，p = 0.15，趋势明显但未达显著
- AgenticX vs OpenCode：10 胜 3 负，p = 0.09，同上
- dsh vs OpenCode：10 胜 8 负，p = 0.81，统计上持平
- Hermes vs OpenCode：7 胜 18 负，p = 0.04，OpenCode 占优

所以严谨的说法是：**AgenticX 显著领先 Hermes 和 Pi，相对 dsh 和 OpenCode 处于第一梯队且趋势占优**。我们不回避这一点——n=1 的评测，8 题的差距需要更多重复实验才能完全坐实。读者在解读任何"XX 榜单"时，也建议带着同样的审慎。

### 2. 机制归因：差距是怎么拉开的

同样的大脑，为什么表现不同？从 trajectory 数据里能看到一些结构性差异（中位数）：

| Harness | 每任务轮次 | 单任务输出 tokens | 上下文消耗 |
|---|---|---|---|
| AgenticX | 33 | 3.5 万 | 210 万 |
| dsh | — | 2.8 万 | 78 万 |
| OpenCode | 26 | 0.5 万 | — |
| Hermes | 27 | 未记录 | — |

三个观察：

- **轮次 × 每轮质量 = 最终成绩**。Hermes 27 轮不算少，成绩却排在 OpenCode 之后——多轮不等于有效轮；OpenCode 输出最精简（中位仅 5 千 tokens），但精简到牺牲了探索深度。
- AgenticX 的画像是有耐心的长跑型：能维持 30+ 轮有效交互不迷失，上下文堆到 200 万 tokens 仍能持续做对决策。**长程任务的胜负手在上下文管理，而不是单轮智力。**
- 一个反直觉的结论：Harness 的价值不在"帮模型做得更多"，而在**帮模型把错误限制在可恢复的范围内**——路径错了能绕回来，上下文脏了能止损。

### 3. 一个差点毁掉实验的事故

dsh 首轮跑完只有 59.6% 的通过率，排查后发现是它的沙箱模式在无头环境下拒绝了所有 shell 命令——Agent 相当于被绑着手参加考试。修复权限配置后从零重跑，通过率拉升到 83.1%，**23 个百分点的差距纯粹来自一行环境配置**。

这件事对所有人都是警示：**Agent 评测里，基础设施问题伪装成能力问题的概率，远比想象的高。** 你看到的低分，可能有相当一部分不是模型蠢，是链路上某处把它掐死了。

## 实验过程中的工程实战

两周的持续运行里踩过的坑，简单列几个：

1. **Docker 崩溃循环**：一次自动更新被中断，留下新旧混装的二进制，组件间协议不匹配导致"unexpected EOF"，整个 Docker 陷入 30 秒崩溃循环。最终通过下载完整 DMG 覆盖安装解决——保留了全部 107 个镜像。
2. **看门狗 + 断点续跑**：实验脚本被会话回收、VPN 节点失效、余额耗尽，任何一项都会让实验静默死亡。最终形态是：watchdog 每 5 分钟检查进程自愈 + 失败任务按轮重试 + 每 5 轮查余额、低于阈值优雅停机。
3. **确定性坏题**：若干题目依赖的 apt 镜像源包已下架（404），所有 harness 一致失败。这类题要在统计口径里剔除或单列，否则会系统性拉低所有人的分。

这套自愈机制让实验在无人值守的情况下跑完了约 500 个 trial，中途经历了 VPN 故障、Docker 重装、多次进程回收——**跑长程评测，工程可靠性是方法论的组成部分，不是附属品。**

## 结论

1. Harness 的差距是真实且量化的：同一模型下，第一名和最后一名差 30.4 个百分点；且第一名对第二名的领先需要用"第一梯队趋势占优"来表述，对 Hermes 和 Pi 则是统计显著。
2. Agent Harness 的核心价值在长程上下文管理和错误恢复，不在单轮的提示工程。
3. 评测基础设施的可靠性，直接决定评测结论的可信度——dsh 那 23 个百分点就是明证。

## Limitations

- 每题每 harness 单次运行，未做多次重复取方差
- 确定性坏题（约 4-5 道）对所有 harness 一致失败，已按同等口径处理
- 各 harness 使用各自的默认 max_tokens 配置（未观测到截断案例）
- Hermes 的 token 用量未落盘（其 result.json 的用量字段为空），机制表中以"未记录"如实标注
- 实验期间网络环境有波动，但任务镜像走本地缓存，评分确定性，不受影响

## 后续工作：跨基准路线图

下一阶段真正值钱的产出不是单榜，而是一个科学问题：**harness 排名是否跨任务分布稳定？**如果 AgenticX 在终端实操和仓库工程两条轴上都第一，结论就从「某个基准上赢」升级为「跨域稳健赢」；如果在代码仓库轴被反超，那也是真发现——harness 与任务域存在适配性。无论哪个结果都有价值。

选型延续本实验的三条铁律：确定性评分 > LLM 裁判、harness 信号 > 模型信号、五个左右 harness 铺满设计光谱；并把本次的教训带上去：k≥3 重复取方差、McNemar 检验常规化。

| 优先级 | Benchmark | 测什么轴 | 为什么值得 | 风险 / 代价 |
|---|---|---|---|---|
| 1 | **SWE-bench-Live**（或 Verified 抽 100 题） | 仓库级代码修复 | 社区认知度最高，与 TB 2.1 形成「终端实操 vs 仓库工程」互补轴；OpenHands 的主场，平台架构在这里才被真正触发 | Verified 有 19.8% 语义假阳性和污染问题，选 Live 规避；全量 500 题贵，抽 100 |
| 2 | **TheAgentCompany**（Princeton） | 长程多应用协作 | 直接强化「长程上下文管理是胜负手」的核心论点；确定性 grader；n=175 | 环境搭建重；部分任务需 GUI 能力，终端 harness 水土不服 |
| 3 | **Aider Polyglot** | 多语言代码编辑 | 便宜、快、确定性单测评分；验证 harness 排名跨任务分布的稳定性 | 社区认知度低，适合快验证而非主战场 |
| 4 | τ²-bench | 多轮工具 + 用户模拟 | harness 循环质量敏感 | 用户模拟器引入随机性，违背确定性原则 |
| 5 | OSWorld / GAIA | 计算机操作 / 通用助手 | 换 harness 品类 | 基建投入大（VM / 浏览器农场），建议单独立项 |

各基准的 harness 阵容（光谱逻辑不变）：

- **SWE-bench-Live**：OpenHands（主场归位）、SWE-agent（研究派极简 scaffold，接替 Pi 的地板生态位）、Aider（git-native 社区主流）、OpenCode（跨基准锚点，验证排名稳定性）、AgenticX（主角）
- **TheAgentCompany**：先以 OpenHands、OpenCode、AgenticX 做可行性探针，跑通再扩
- **Aider Polyglot**：Aider、OpenCode、dsh、AgenticX——两三天出结果的快验证

**第一步**：Aider Polyglot 低成本试点（验证流水线跨基准迁移成本），同时评估 harbor registry 对 SWE-bench-Live 的收录情况——未收录则需写 dataset adapter，工作量可控。
