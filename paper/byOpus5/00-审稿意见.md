## Reviewer #1（基准方法学方向，Confidence 4）

**Rating: 3 — Reject**

### Summary

作者提出 TeamBench，一个用于配对比较"单智能体"与"角色分工团队"的办公任务基准，包含 15 个中文办公任务（5 场景 × 3 耦合度），在 5 个模型上跑了 300 次运行，提出 CTR（能力转化率）等团队级指标，报告了"团队系统性损耗个体能力 4–7%"等 5 个发现。

### Strengths

- S1. 问题定位准确。现有 agent 基准确实以单智能体为分析单位，"加 agent 到底赚不赚"这个问题确实没有基准在正面回答。这是一个真实的空白。
- S2. 配对设计（同一任务的 single/team 两种模式共用同一打分协议）在方法上是正确的思路，比事后横向对比不同论文的数字要严谨得多。
- S3. §5.7 主动报告了哪些结论不显著，并在正文中标注"underpowered"，这种统计诚实度高于本 track 的平均水平，值得肯定。

### Weaknesses

- **W1（致命）。团队模式的"产出"定义不成立。** 从 `paper/infra/teambench_runner.py:301` 可见，团队的最终交付物被定义为**最后一个角色的输出**，前面所有角色的产出被直接丢弃。而团队角色的 system prompt（同文件 L186–191）明确要求每个角色"只输出你分内的交付物"。于是在 `t-CONTENT-H-03` 这类任务里，团队实际产出了主演讲稿、竞品对比、技术 Q&A、业务 Q&A 四个部分，但只有第四部分进入打分，而打分标准要求四部分齐全——团队因此被扣掉它明明完成了的工作的分。这不是"团队协作损耗能力"，这是评测管线丢数据。论文的第一号发现建立在这个 bug 上。
- **W2（致命）。这个 bug 的效应量压倒了论文所有报告的效应。** 我按"最后一个角色是否承担整合职责"把 15 个任务分成两组重算：整合型收尾的任务平均 CTR 1.03，切片型收尾的任务平均 CTR 0.87。在控制耦合度之后，低耦合档内部两组差 0.276，高耦合档内部差 0.270。而论文的三个主发现效应量分别是 −0.047（团队次优）、−0.017（能力转移悖论）、+0.077（PROJ 甜蜜点）。**一个未受控的工程变量的影响是全部科学发现的 3–6 倍。** 在这种信噪比下，论文报告的任何效应都无法归因。
- **W3（致命）。Finding 1（CTR 随耦合度单调递增）在控制该变量后消失。** 整合型收尾任务的 CTR 在低耦合是 1.041、高耦合是 1.020（略降）；切片型收尾任务在低耦合 0.765、高耦合 0.750（略降）。两组内部都不随耦合度上升。之所以合并后看起来单调，是因为整合型任务在三个耦合档的占比是 3/5、0/5、4/5——这是教科书式的 Simpson 悖论。
- **W4。"抗污染的参数化任务"这一主张在代码中不存在。** `paper/tasks/task_generator.py:607-609` 的 `_apply_param_variant` 函数体是 `return obj`，注释写着"v0.1 参数化表达式暂不启用"。所谓"变体"是逐字节相同的副本，只有 `variant_id` 不同。但 Abstract 写"15 parameterized office tasks"、Table R1 的 Contamination defense 一栏标 ✓、§4.1 声称"enabling contamination-resistant regeneration"。稿件声称了一个不存在的能力。
- **W5。规模不满足本 track 对数据集类投稿的期待。** 15 个任务，对照 TheAgentCompany 175、GAIA 466、OSWorld 369。作者自己在 §7 承认每格 n≈10。作为 benchmark 贡献，可复用性存疑。

### Questions

1. 团队的四个角色都产出了内容，为什么只有最后一个进入评分？如果改为把四个角色的产出按章节拼接后再打分，CTR 会变成多少？
2. 参数化变体生成器实际生成的变体之间有任何差异吗？请给出两个变体的 diff。
3. 单智能体获得 4000 字预算、团队每角色 2800 字预算，但团队最终只有一个角色的输出进入评分——这是否意味着团队产物的字数上限只有单体的 70%？打分中大量依赖"必需章节/元素是否出现"，这个上限差异如何排除？

### Limitations

作者列了 7 条 limitation，但没有一条提到产出装配方式。这恰恰是最大的威胁效度。

### Ethics

`t-CONTENT-H-03` 任务数据中包含作者所属项目的产品名，以及三个真实开源项目（AutoGen / CrewAI / LangGraph）的"weakness"字段。作为公开发布的数据集，前者破坏双盲、后者是对第三方项目的负面断言。需要处理。

## Reviewer #2（多智能体系统方向，Confidence 5）

**Rating: 2 — Strong Reject**

### Summary

同上。

### Strengths

- S1. CTR 的形式化定义清晰，与 Woolley 集体智能因子的对标是一个合理的理论锚点。
- S2. 跨厂商 judge 矩阵（判分模型永远来自与被判模型不同的家族）是一个好的设计细节。

### Weaknesses

- **W1（致命）。论文评测的对象不是多智能体系统。** `LightweightTeamRunner`（`teambench_runner.py:280-317`）的实际行为是：按固定顺序对每个角色发起一次 LLM chat completion，把上游输出截断到 4000 字符塞进下游 prompt，没有 agent loop、没有工具调用、没有共享工作区、没有消息总线、没有任何角色可以回退或质询上游、没有终止条件判断。这是一个**静态提示链（static prompt chain）**，不是 agent 团队。论文标题、Abstract、Introduction、Discussion 全篇以 "multi-agent LLM teams" 立论，并在 §6 给 AutoGen/CrewAI/LangGraph/MetaGPT 的框架开发者提建议——但这四个框架**一个都没跑**。从一个手写的三次串行 API 调用，外推到整个多智能体框架生态，构念效度（construct validity）不成立。
- **W2（致命）。计算预算不对等，比较无意义。** 团队消耗 2.4–3.4× token 与 3–4× LLM 调用，单体只有 1×。论文据此得出"团队更贵且更差"。但正确的对照应该是**同等算力下的单体**：k 轮 self-refine、best-of-k 采样加选择、或者单体给 k× 输出预算。这是 More Agents Is All You Need 之后该领域的标准做法。缺了这一组，"团队不划算"的结论无法与"你只是没给单体同样的钱"区分开。
- **W3。论文宣称的指标套件有一半从未测量。** Contribution 第二条写 "a formal team-level metric suite (CTR, CO, PC, TMS)"。但按 `paper/metrics/团队级指标形式化定义-v0.1.md` §8 的自述表，PC / RT / AC / MC / MR / WIR 全部是"❌ 无"或"⚠️ Phase 2 补"。实验部分也确实一个数字都没报。把未实现的指标写进 contributions 是过度声称。
- **W4。§5.5 提出的 "semantic relay penalty"（中耦合档在 L3 打开后掉得最狠）被包装成一个 benchmark-design finding，但它更可能就是 W1 的直接后果。** 中耦合档的 5 个任务里，最后一个角色承担整合职责的数量是 **0/5**——五个任务的团队产出全都是残缺切片。中耦合掉得最狠不需要"语义在接力中衰减"这样的理论，只需要"这一档全部丢了产出"。作者为一个 bug 发明了一个术语。
- **W5。"能力转移悖论"（更强的模型协作更差）的证据链太弱，不足以进 Abstract。** 论文自己报告 DS 家族 p=0.137、Kimi 家族 p=0.851，两个都不显著；第三个家族只有一个模型，无梯度可言。且 GLM 走的是聚合平台而其他模型走一方端点（作者 Limitation 6 自承），供应商路由差异与"能力档位"完全混杂。此外 Kimi 系列被 API 强制 temperature=1.0 而 DS/GLM 用 0.3（`teambench_runner.py:59-63`），跨家族比较又叠了一层采样温度混杂。用三个混杂变量支撑一个方向性结论并写进 Abstract，是不可接受的。

### Questions

1. 为什么不用仓库里已有的 `AgentTeamManager`？立项计划 §2.4 明确写了要基于它搭建，`paper/infra/team_spawn_smoke.py` 也存在，但主 runner 完全没用。是遇到了什么障碍？
2. 如果给单体 3× 的 token 预算（例如三轮自我修订），CTR 还小于 1 吗？
3. Kimi 在 temperature=1.0 下 seed 参数根本没有传（见 `LLMClient.call` 的 `if seed is not None and self.temperature != 1.0`）。那么 Kimi 的"两个 seed"在什么意义上是可复现的？

## Reviewer #3（评测与统计方向，Confidence 4）

**Rating: 3 — Reject**

### Strengths

- S1. 报告了 Wilcoxon / Mann-Whitney 而不是只报均值，方向正确。
- S2. §5.7 的 "Honest reading" 段落对哪些结论强、哪些弱做了区分，态度端正。

### Weaknesses

- **W1（致命）。质量分 Q 缺乏效度证据，且打分函数本身奖励冗长。** 三处具体问题：
  - **L1 结构分实际是字符袋检验。** `teambench_runner.py:349-353`：`words = [c for c in re.sub(...)]` 把章节名拆成**单个汉字**，然后 `hits = sum(1 for c in words if c in output)` 检查每个字是否在全文任意位置出现。于是"本周进展"这个章节只要全文里分别出现过"本""周""进""展"四个字就算命中。输出越长，命中概率越高。
  - **L2 数值分实际是"文中离目标最近的那个数"。** 同文件 L434-437：`nums = [所有数字]; best = min(nums, key=lambda n: abs(n-tgt))`。输出里数字越多，越可能有一个碰巧接近目标值。这不测正确性，测的是产出里数字的密度。
  - 两者叠加的后果：**Q 与输出长度正相关**。而单体被允许 4000 字、团队最终产物只有一个角色的 2800 字（且常常只是残片）。所谓"团队质量更低"至少有一部分是"团队产物更短"的同义反复。作者从未报告长度控制后的结果。
- **W2（致命）。基线实验中 L3 恒为常数 0.6，导致 Q = 0.5·L1 + 0.3·L2 + 0.12，CTR 是一个含固定加性偏置的比值。** 分子分母同加常数会把比值系统性地拉向 1，主结果表里所有 CTR 都被人为压缩。§5.5 打开 L3 后 CTR 普遍下降 0.05–0.06，作者解读为"语义质量被计入后团队损失更大"，但其中有多少是去掉常数项的机械效应，论文没有分离。
- **W3。指标文档承诺的多重比较校正没做。** `团队级指标形式化定义-v0.1.md` §5 末句写"所有 p 值做 Benjamini-Hochberg FDR 校正"。稿件 §5.7 报了十余个 p 值，无一处提到 FDR。
- **W4。TMS 的定义在文档与代码之间漂移。** 文档 §3 定义为"所有断言全通过"的二元指示函数；代码 `teambench_runner.py:492` 实现为 `sections_pass and (l2_score >= 0.5)`，注释自承"降低门槛，避免零分误判"。而 §5.4 又把它当作一个百分比（"83%→63%"）来报告。三个地方三种含义。
- **W5。CTR 用均值-比值（mean of ratios）聚合，有已知偏差，且在 Q_single 较小时方差爆炸。** 应同时报告配对差值 ΔQ、log 比值的均值、以及 bootstrap 置信区间。当前只有点估计。
- **W6。功效严重不足且未做功效分析。** 15 任务 × 2 seed = 每模型 30 对，每格约 10。作者自己承认。以观察到的效应量（0.02–0.05）计，检验出跨家族梯度所需样本量远超当前规模。

### Questions

1. Q 有没有和人工评分比对过？相关系数是多少？（指标文档 §9 把这项列为待办且未勾选）
2. 如果把 L1 从字符包含改成"必须出现规范化的章节标题"，主结论还成立吗？
3. 报告 CTR 时能否给出按输出长度分层或回归调整后的版本？

## Area Chair 元评审

**Decision: Reject**
**Confidence: High**

三位审稿人独立给出 2/3/3，且**三人各自从不同专业角度指向同一个根因**：团队模式的产出装配方式（R1 从基准方法学、R2 从系统构念、R3 从统计混杂）。这种独立收敛通常意味着问题是真实且结构性的，而非审稿人误读。

我另外核实了两项，都属于需要在任何重投之前解决的问题：

**（一）参考文献存在疑似伪造条目。** 抽查 bibtex：`bara2025agentsroom` 条目写作者 "Bara, Grace and others"、arXiv 2503.19498；而 Agents' Room 的真实出处是 Huot et al., ICLR 2025, arXiv:2410.02603，作者与编号均不符。`chen2024morellmcalls` 的作者列表出现 "Davis, Davis"。`zhu2025multiagentbench`、`han2024llmmultiagentsurvey` 的作者列表同样可疑。在 A 类会议，伪造引用会触发学术不端流程，而不只是拒稿。**投稿前必须逐条核验全部 22 条引用。**

**（二）双盲与第三方风险。** 稿件的数据资产位于作者所属开源项目的主仓库路径下，且 `t-CONTENT-H-03` 的任务内容直接使用该项目产品名作为被宣发对象，并列出三个真实竞品的"弱点"。这既构成匿名性泄露，也意味着一个公开基准的任务数据里嵌入了对第三方项目的负面评价。需要在发布前清洗。

**给作者的建设性意见（我认为这项工作值得重投）：**

这个选题的缺口是真实的，配对设计的思路也是对的。真正的问题是，你们把一个**未受控的设计变量**当成了噪声，而它其实是你们数据里最强的信号。审稿人 #1 重算的那张表——低耦合档内整合型 1.041 vs 切片型 0.765，高耦合档内 1.020 vs 0.750——如果把它从"混杂"改写成"受控因子"，你们就有了一篇更好的论文：

> 多智能体团队是否划算，主要不由模型能力或团队规模决定，而由**产出装配协议**决定。

这个主张有三个优点：它是条件性的（审稿人喜欢条件性结论胜过全称否定）；它解释了为什么此前文献结论互相打架（各家装配方式不同且从不报告）；它给框架开发者可执行的行动项（D&B track 看重这个）。而且**你们已有的 300 次运行不作废**——它们成为 `assembly=last` 这一实验臂。

重投时我希望看到：装配协议作为受控因子的完整析因实验、算力对等的单体基线、经过人工验证的打分函数、真实可用的参数化生成器、至少两个真实多智能体框架的适配、以及规模上到 45–60 个任务。

## 从"拒稿"到"接收"的最短路径（优先级排序）

按"每单位工作量能挽回多少分"排序，前三项占了总收益的约 70%：

1. **修复产出装配并把它变成受控因子**（`01` B1 → `02` FIX-1 → `03` 实验一）。这一项同时解决 R1-W1/W2/W3、R2-W4、AC 的核心关切，并把论文主张升级。**投入 3 周，收益最大。**
2. **补算力对等的单体基线**（`01` B7 → `02` FIX-2）。解决 R2-W2，这是该领域标准要求，不补必被追问。**投入 1 周。**
3. **重写打分器 + 人工效度验证**（`01` B3 → `02` FIX-3 + FIX-6）。解决 R3-W1/W2 和 R1 的追问 3。**投入 3 周（含标注）。**
4. 清理学术诚信问题：引用核验 + 匿名化（`01` B5/B6 → `04` §5 + `05`）。**投入 3 天，但不做就是零分。**
5. 实现真实参数化生成器（`01` B4 → `02` FIX-4）。**投入 1 周。**
6. 任务扩容到 45–60 + 至少 2 个真实框架适配（`03`）。**投入 6 周。**
7. 统计升级：混合效应模型 + FDR + bootstrap CI（`02` FIX-5）。**投入 1 周。**
8. D&B 交付物补齐（`05`）。**投入 1 周。**

详细实施见 `02-代码修复规范.md` 与 `03-实验设计与执行手册.md`。
