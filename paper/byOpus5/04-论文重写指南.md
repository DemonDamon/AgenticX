## 1. 新叙事主线

### 1.1 建议标题

> **TeamBench: Assembly Protocol, Not Model Capability, Determines Whether LLM Agent Teams Pay Off**

备选（更中性，若数据不支持强主张）：

> **TeamBench: A Paired Benchmark for Measuring When Multi-Agent LLM Teams Outperform Single Agents**

### 1.2 一段话主张（写 Introduction 时的锚）

现有关于"多智能体是否优于单智能体"的结论互相矛盾，一个被忽视的原因是：**这些工作从未报告团队产出是如何装配的**。我们通过配对式个体—团队评测发现，仅仅改变团队最终交付物的装配方式（取末位角色输出 / 确定性拼接 / 专职整合角色 / 共享黑板），CTR 就会发生远大于模型能力差异的变化。TeamBench 把装配协议提升为一等受控变量，并提供第一个能分离"协作收益"与"装配损耗"的测试床。

### 1.3 三条支撑论点

| 论点 | 需要的数据 | 来源 |
|---|---|---|
| P1. 装配协议是 CTR 的主导因子，方差解释比高于模型能力与耦合度之和 | Exp1 方差分解 | `03` §6.1 |
| P2. 在正确装配下，团队在高耦合任务上稳定跑赢算力对齐的单体 | Exp1 的 integrator × H 单元 vs `single_refine_k` | `03` §6.1 |
| P3. 主流框架的默认装配方式恰是最差的一种，因此文献中的"多智能体无效"结论部分是实现假象 | Exp3 框架实验 | `03` §6.3 |

**如果 P1 不成立**，走 `03` §8 的备用叙事。

## 2. 逐节写作规范

### Abstract（150–200 词）

必须包含且只包含**有数据支撑**的内容：

```
[缺口] 现有 agent 基准以单智能体为分析单位，无法回答"加 agent 是否划算"。
[方法] TeamBench：45 个参数化办公任务（5 场景 × 3 耦合 × 3 实例，450 个变体），
       配对式个体—团队评测，7 条执行臂（3 条算力对齐的单体基线 + 4 种装配协议）。
[规模] N 个模型 × M 个框架 × 3 seeds = K runs。
[结果] 装配协议解释 CTR 方差的 X%，模型能力仅 Y%（X >> Y，p=...）。
       在 integrator 装配下，高耦合任务的 CTR 达到 Z（95% CI [...]），
       显著高于算力对齐的单体基线；在 last 装配下降至 W。
[效度] 打分器与人工评分 Spearman ρ = ...，标注者间 α = ...。
[发布] 任务、生成器、runner、rubric、全部轨迹开源。
```

**禁止写入 Abstract 的内容**：任何 p > 0.05 的方向性结论（v0.5 把 p=0.137 / p=0.851 的"能力转移悖论"写进了 Abstract，这是审稿人明确点名的问题）。

### §1 Introduction

四段结构：

1. **多智能体的承诺与现实分歧**。框架繁荣，但"是否真的更好"结论打架，举 2–3 个互相矛盾的文献。
2. **缺口诊断**。指出分歧的一个未被讨论的来源：产出装配方式从未被报告或控制。**这里可以诚实地讲自己的经历**——"我们最初的实现采用末位角色输出，得到了'团队普遍更差'的结论；在把装配方式改为受控变量后，同一批任务同一批模型的结论发生反转"。这种自述会大幅提升可信度，D&B 审稿人尤其吃这一套。
3. **TeamBench 的三个设计原则**：配对模式、装配协议受控、算力对齐基线。
4. **贡献列表**（见 §3）。

2. **§5.2 控制装配后的耦合度效应**（回应 Simpson 悖论，Figure 4）

每个 Finding 的写法模板（严格遵守）：

```
**Finding N（一句话标签）.** 
[现象] 数字 + 95% CI + 检验统计量 + p（BH-FDR 校正后）+ 效应量。
[范围] 在哪些模型/场景/耦合档成立，哪些不成立。
[机制] 从 artifact 中找到的具体证据，引用附录的样例编号。
[反例或边界] 诚实说明什么情况下不成立。
```

**硬性要求**：任何一个 Finding 若 p > 0.05，标题必须写成"趋势"而非"效应"，且不得进入 Abstract 与 Conclusion。

### §6 Discussion

三块：

1. **对实践者**：什么任务用团队、用哪种装配、预算怎么算。给一张决策表。
2. **对框架开发者**：主流框架默认装配方式的问题；建议暴露装配协议为一等配置项。
3. **对基准设计者**：本文最有价值的方法学教训——**报告装配协议应成为多智能体评测的必备项**，就像报告 temperature 一样。可以提议一个最小报告清单（minimal reporting checklist）。

### §7 Limitations

诚实列出，至少包括：中文为主（若已做英文子集则说明覆盖比例）、任务为合成办公场景、团队拓扑固定（无自组织）、无长程工具使用、闭源模型覆盖有限、运行时开环（保留 v0.5 §6 的讨论）。

## 4. 写作质量红线

1. **不得复用 v0.5 的任何结论句**。数据变了，句子必须重写。
2. **每个数字必须能在 `paper/experiments/v2/` 下找到出处**。建议在 markdown 草稿中用 HTML 注释标注来源：`<!-- src: exp1_dsflash_integrator/pairs.csv col CTR_matched -->`，LaTeX 化时再删除。

## 6. Rebuttal 预演（提前准备答案）

审稿人几乎必问的 8 个问题，写作时就应在正文或附录中提前回答：

| # | 预期提问 | 应在哪里回答 |
|---|---|---|
| 1 | 你们的"团队"有 agent loop 和工具吗？还是只是提示链？ | §4 明确说明执行模型；Exp3 用真实框架回应 |
| 2 | 给单体同样的算力它会不会也变好？ | §4.y + §5.3（这正是 compute-matched 基线的意义） |
| 3 | 打分函数怎么保证不是在奖励长输出？ | §4 打分协议 + §5.5 效度 + 附录长度控制分析 |
| 4 | 装配协议的差异是不是就是"多一次 LLM 调用"？ | 必须报告 integrator 的额外开销并做对照：给 last 协议也追加一次同等开销的无效调用 |
| 5 | 15→45 个任务够吗？和 TAC 175 比呢？ | §7 Limitations 诚实说明，并强调本文的贡献是**受控设计**而非规模 |
| 6 | 中文任务的结论能推广到英文吗？ | §5 报告英文子集结果 |
| 7 | 参数化变体真的不同吗？ | 附录给出变体 diff 样例 + `validate_variants.py` 的输出 |
| 8 | 为什么没有 GPT/Claude？ | 必须至少有一个闭源模型，否则这个问题无法回答 |

**第 4 条特别重要**：integrator 协议比 last 多一次 LLM 调用，审稿人会怀疑效应只是"多算了一次"。**必须设置对照臂**：`last_plus_dummy`——在 last 协议后追加一次同等 token 量但不改变产出的调用（例如让模型复述），证明效应来自装配逻辑而非额外算力。**把这条加进 `03` §6.1 的实验臂**。
