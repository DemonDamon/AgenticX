# 竞品基准差异化分析备忘

> Phase 0 / W1 产出
> 日期：2026-08-20
> 对比对象：TheAgentCompany (TAC) / OSWorld 2.0 → TeamBench

---

## 一、竞品基准精读

### 1. TheAgentCompany (TAC)

- **来源**：CMU + Duke，NeurIPS 2025 Datasets & Benchmarks Track（poster，已接收）
- **arXiv**：2412.14161v3，2025-09 更新
- **环境**：自包含 Docker 沙箱，模拟小型软件公司，内网服务用开源替代品（GitLab / OwnCloud / RocketChat / Plane）
- **任务**：175 个长程任务，跨 7 类职业角色（SDE / PM / HR / Finance / Admin / QA / DS）
- **交互**：Agent 与 LLM 驱动的"模拟同事"通过 RocketChat 通信——但本质是单 Agent 与 NPC 交互，非真正的多 Agent 团队分工
- **评测**：checkpoint-based rubrics + 部分分数；子集 checkpoint 用 LLM grading 做简单抽取/分类
- **指标**：任务成功率（自主完成）、部分完成率、步数、成本（$/task）
- **最佳结果**：Gemini-2.5-Pro，30.3% 自主完成，39.3% 部分完成，平均 $4.2/task
- **关键发现**：
  - 软件工程类任务表现最好（>30%），行政/财务类最差
  - RocketChat（社交交互）和 OwnCloud（复杂 Web UI）是主要失败点
  - 长程任务仍是当前系统能力边界
- **审稿人评价（OpenReview）**：贡献清晰、社区价值高；批评点在用了默认 CodeAct Agent 无优化、未公开 prompt

### 2. OSWorld 2.0

- **来源**：XLANG Lab (HKU) + 多校合作，arXiv 2606.29537
- **环境**：真实 VM 内的真实 OS 应用（文件管理器、浏览器、LibreOffice、命令行）
- **任务**：108 个长程计算机使用工作流，中位人类完成时间约 1.6 小时
- **评测**：执行状态核验（脚本检查 VM 最终态，pass/fail），不用 LLM judge 做主判据
- **指标**：二元完成率（500 步内）、部分分、平均步数、评分检查点数
- **最佳结果**：Claude Opus 4.8 max-thinking + batched tool calls，20.6% 完成，54.8% 部分分；GPT-5.5 更省 token 但仅 ~14%
- **关键发现**：
  - 平均需 318 次工具调用（vs OSWorld 1.0 约 30 次）
  - 69.6% 任务超过 1 小时
  - 失败主因不是基础 GUI 操作，而是"丢失目标追踪"——长程下注意力漂移
  - 覆盖流式交互、动态环境、跨源推理、隐式状态推断、视觉空间精度等挑战现象

## 三、TeamBench 差异化主张（卖点提炼）

### 主张 1：分析单位从"个体"升到"团队"
TAC 有"模拟同事"但本质是单 Agent 与 NPC 对话，不是多 Agent 分工协作；OSWorld 2.0 纯单 Agent。**没有任何主流基准测量"团队级产出"**。TeamBench 首次以团队为分析单位。

### 主张 2：能力转化率（Capability Transfer Rate）为首创指标
TAC/OSWorld 的指标全部是个体任务成功率及其变体。TeamBench 引入"能力转化率 = 团队产出 / 个体产出加和"，直接对标 Woolley 集体智能因子，但用于人机混合团队——这个交叉点学界还没人占。

### 主张 3：协调开销为一等指标
现有基准最多报告步数和成本，**没有任何基准测量"协调本身的开销"**（通信轮次、Token 冗余、等待空闲）。TeamBench 把协调开销作为一等指标，支撑"协作税"的核心叙事。

### 主张 4：抗污染动态生成
TAC 和 OSWorld 都是静态固定任务集，存在数据污染风险（尤其是 OSWorld 被批"训练数据污染"是已知问题）。TeamBench 用参数化模板批量生成变体，从设计上对抗污染——这正好踩中"living benchmark"评审呼吁方向。

### 主张 5：过程感知
TAC/OSWorld 主要判结果。TeamBench 测量协议合规度（角色越权率、任务认领冲突、结果合并冲突），把"怎么协作"纳入评测，而非只看"有没有完成"。

## 四、风险确认

1. **撞车风险**：TAC 已在 NeurIPS 2025 D&B 占位"办公场景 Agent 基准"。TeamBench 必须在"团队级 vs 个体级"这个轴上做足差异化，不能被审稿人归为"TAC 的扩展"。
   - **对策**：Introduction 第一段就点明"TAC 测单 Agent 在公司里的表现，我们测多 Agent 团队的协作产出"，并在 Related Work 表里显式标注 TAC 的"NPC 交互 ≠ 多 Agent 团队分工"。

2. **"团队次优"现象须可复现**：整个论文的卖点依赖"个体最优、团队次优"现象。若复现不出，叙事塌方。
   - **对策**：Phase 0 W2 的 3 个种子任务试跑就是验证这一点的决策门。

3. **任务真实性**：TAC 用真实开源工具搭公司环境，真实感强。TeamBench 若用合成办公场景，可能被批"不够真实"。
   - **对策**：任务设计基于公司真实办公工作流抽象；若公司允许，用脱敏真实数据校准。
