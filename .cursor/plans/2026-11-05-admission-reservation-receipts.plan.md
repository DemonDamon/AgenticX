# Admission reservation receipts

Planned-with: gpt-6.1-sol
Suggested-Impl-Model: gpt-6.1-sol

## Evidence

`enterprise/apps/gateway/internal/quota/check_request.go::CheckRequest` reserves daily tokens before weekly checks and monthly tokens before budgets, but later denial only releases concurrency. `billing/service.go::SettleContext` reselects current monthly rules/windows and ignores day/week. Server direct/channel/cache/protocol exits differ; channel completion omits budget receipt. Database pool updates and ledger insertion are separate operations.

## Implementation

1. Add `internal/quota/reservation_receipt.go`: pointer-owned receipt recording each successful day/week/month token precharge, original key/period/rule/amount, existing BudgetReceipt and captured concurrency release callback. Mutex protects first terminal outcome and per-line completion. Retry only incomplete operations against the first selected outcome.
2. `CheckRequest` creates/returns receipt and compensates on later rejection. RPM and request-count consumption remain admission-attempt counters and are never refunded. Warnings continue subsequent checks. Legacy non-receipt APIs remain.
3. `FinishReservation(receipt, actualTokens, actualCost)` adjusts original rows by actual-minus-reserved without current rule selection, with per-line completion and request-ID idempotence. Zero-output failure uses zero. `ReleaseReservation` releases only an acquired original key exactly once, including after config change.
4. Database pool Add: in one transaction ensure/lock original usage row, check request/event ledger deduplication, update usage and append ledger then commit. No counter-table shape changes. The request-index upgrade is specified below. Configured database storage unavailable returns error, never local fallback.
5. Server `reportUsageDetailed` settles receipt with actual usage/cost; all admitted chat/protocol requests defer unfinished zero-usage compensation plus release. Private identity/context fields propagate receipt through routing changes. Receipt-aware branches bypass legacy monthly reconciliation. Billing helpers retain compatibility. Do not change embedding admission in this PR.

## Request lookup index follow-up and deployment dependency

`PGPoolCounter.mutate` performs a request-ID equality COUNT and reserve-event SUM while holding the usage row lock. Both original schema definitions and published migrations only indexed tenant/scope/period, so growing per-window ledgers could force scanning an entire scope during this critical section. Add non-unique `gateway_quota_ledger_request_idx(tenant_id, scope_type, scope_id, period, request_id, event)` to both schema definitions and new upgrade SQL. The request prefix serves deduplication; the final event column also serves the original-reserve equality predicate. Keep the old scope index and all published baseline SQL unchanged.

- Incremental files: PostgreSQL `drizzle/0076_gateway_quota_ledger_request_index.sql`; other dialect `drizzle-mysql/0050_gateway_quota_ledger_request_index.sql`. Identity PR #261 already owns0075/0049 and journal idx74/49; these index entries use idx75/50, preserving those reserved slots rather than reusing them. Their timestamps strictly follow the identity entries.
- The existing `scripts/db-migrate.mjs` selects the dialect configuration and invokes the standard migration command. The installed journal reader was inspected: SQL is loaded by entry.tag, entry.when is the migration watermark; idx gaps do not skip SQL. New unit contracts invoke that actual reader and assert the index definition and preserved inventory.
- **Migration dependency:** merge/apply #261 identity migrations before this index, or reconcile both journals and apply one ordered deployment containing both. Do not deploy this later-watermark index and only afterwards insert the older identity entry: the standard watermark-based runner would skip that older migration. This task publishes reviewable changes only and performs no deployed migration.
- The dedicated storage workflow now triggers on db-schema changes, runs schema parity/contracts, invokes the normal complete migration chain twice on disposable databases, then runs the live budget/receipt contracts. The Go fixture never creates the new index; it queries actual catalog metadata for all six columns, executes the exact request equality COUNT and reserve SUM predicates, and preserves the original8-way completion retry assertion.
- DDL builds a new index using the standard transactional migration path; an existing large ledger needs an appropriate migration/maintenance window because ordinary index creation can block writes. No historical data, index deletion or unrelated schema changes are introduced.
