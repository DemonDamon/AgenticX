# AGX Rules & Knowledge Suite：规则与知识证据底座主线规划

Planned-with: glm-5.3
Status: draft（规划评审稿，粗粒度主线）
需求依据：`docs/agx-rules-knowledge-suite/requirement-background.md`（已脱敏）

## 目标

为 AGX 补齐「业务规则智能生成 + 知识证据」方向的通用底座能力，使 AGX 在面对规则配置类（合规审计规则、运维业务规则、指标规则）与知识证据类（本体建模、证据化检索、作业辅助）项目时，只需少量项目侧配置与适配即可交付，无需每个项目从零重复建设。

本规划源于一次真实售前项目的能力覆盖度摸底（见需求依据文档）：AGX 主干对该项目能力域（610 人天）的覆盖度约 49%，通用能力缺口 ≈190 人天，缺口集中在「规则实体」「证据结构」「知识生命周期」「消歧交互」四类通用能力上。

目标态：本套能力落地后，此类项目的能力域覆盖度提升至 **75%~80%**，剩余 10~20% 为领域字典、源系统适配与工程定制（B 层）。

## 规划原则：与 AGX Data Suite 相同的 A/B 解耦纪律

```
交付逻辑 = A（通用能力，进主干）→ + B（项目定制，配置 + 插件实例 + 少量适配）→ 交付
```

- 引擎只认通用语义：规则、对象、证据、词典全部外置为配置；**任何行业专名不得进入引擎代码**。
- 定制需求进项目层之前先问：「能不能用 A 的配置表达？」——防止项目专属逻辑渗漏进主干。
- 规则 → 执行的编译层必须**目标引擎可插拔**：编译到 AGX Flow 是默认 backend，编译到外部引擎规范是插件 backend（本条源于真实项目教训：客户侧既有引擎接口规范可能事后才给）。
- 效果类能力必须内置量化评测基准（规则生成准确率、消歧命中率、引用忠实度），评测集以配置形态提供样板、以项目实例落地。

## 能力组（粗粒度）

### R1 规则资产与规则引擎（Rule Assets & Rule Engine）— P0 · ≈100–120 人天

当前 AGX 有工作流编排（`agenticx/core/workflow_engine.py`、`agenticx/flow/`）但没有「规则」这个一等公民实体——规则散落在 data-suite 治理 YAML、安全 policy 与各项目代码里，无生命周期、无可视化、无 NL 生成链路。这是最大单项缺口，也是跨项目复用价值最高的一块（合规审计规则、运维规则、指标规则同构）。

- **能力**：
  1. 规则实体模型：CRUD、版本、启停、审核流、审计、状态机（草稿—待生效—生效—停用—归档）、规则元数据（适用范围 / 优先级 / 触发方式 / 依赖资源）；
  2. 规则 DSL：按「数据对象—触发条件—判断逻辑—执行动作—结果反馈」结构的声明式表达，要素（对象 / 条件 / 阈值 / 动作）可映射到统一数据模型、OpenAPI 工具或已注册 MCP 工具；
  3. NL → 规则生成链路：意图识别（创建 / 修改 / 查询 / 测试执行）→ 要素抽取 → 结合词典与元数据的**歧义校核与候选确认** → 结构化规则草稿 → 校验（语法 / 参数 / 类型 / 接口可用性 / 权限）→ 人工确认入库，全程版本留痕；
  4. 规则 → 工作流编译：规则 DSL 编译为 Flow / workflow_engine 可执行任务流，状态与异常（排队 / 执行中 / 完成 / 异常 / 重试 / 终止）回写规则实体；外部引擎 backend 以插件形态挂接；
  5. 执行可视化数据模型：触发记录、节点进度、异常位置、历史结果，支撑前端流程图渲染；
  6. 评测基准：规则生成准确率、要素抽取命中率、编译成功率的标准评测集与跑分入口。
- **落点**：`agenticx/rules/`（新顶层包）；`agenticx/runtime/confirm.py` 复用为确认门控；`enterprise/apps/admin-console` 新增「规则治理」域（列表 / 版本 / 执行记录 / 流程可视化页面）。
- **验收**：一条自然语言规则经「生成 → 确认 → 入库 → 编译执行 → 状态回传 → 前端流程可视化」全链路跑通；规则全生命周期零引擎改动可配置；评测基准可跑分。
- **价值**：把散落各项目的规则建设收敛为一次产品能力；直接补齐售前摸底中 M1 域 38% → ≈75%。

### K1 证据与引用结构（Evidence & Citation）— P0 · ≈20–30 人天

现状：`agenticx/knowledge/graphers/spo_extractor.py` 的抽取结果已带 `evidence` / `source_chunks` 字段，但检索结果（`agenticx/retrieval/base.py` 的 `RetrievalResult`）没有系统性的来源引用结构；「以对象为中心聚合证据」完全缺失。

- **能力**：
  1. `RetrievalResult` 统一 provenance 标准字段：来源类型（结构化记录 / 图关系 / 文档条款 / 推理摘要）、来源标识、数据时间、置信度、原始上下文指针；
  2. 对象中心证据包（Evidence Bundle）：以实体标识为中心，聚合台账属性、关联记录、图关系、文档条款为标准证据结构，供智能体一次调用；
  3. 上下文组装策略：按信息重要性、时间有效性、来源可信度组装，输出「结构化数据 + 可读摘要 + 来源依据 + 缺失 / 冲突提示」；
  4. 前端引用展示标准化：web-portal 对话与 admin-console 统一引用 / 冲突并列展示组件。
- **落点**：`agenticx/retrieval/base.py` 扩展；新增 `agenticx/retrieval/evidence.py`；`agenticx/knowledge/search_orchestration.py` 复用；web-portal 组件标准化。
- **验收**：任一检索路径返回的结果均携带完整 provenance；证据包一次调用返回多源证据且缺失 / 冲突有显式提示。
- **价值**：证据化输出是所有知识类项目的验收硬指标，一次建设全线复用。

### K2 知识对象生命周期与质量治理 — P1 · ≈20–25 人天

现状：`agenticx/data_suite/governance/` 已有 quality / cleaning / lineage，但知识对象没有生命周期状态机与质量问题清单闭环。

- **能力**：知识对象状态机（草稿—待审核—已发布—已失效）+ 变更追溯；质量问题检查（标识关联、必填属性、关系完整性、重复、冲突、失效）生成问题清单并跟踪处理状态；与 `data_suite/idmapping/`（主索引合并、冲突策略、快照回放）联动实现实体级治理；审核动作对接 RBAC 与审计日志。
- **落点**：`agenticx/data_suite/governance/` 扩展 + `agenticx/knowledge/` 挂接；admin-console「数据治理」域增页。
- **验收**：一批多源知识对象经「接入 → 质量检查 → 问题清单 → 审核 → 发布 / 失效」闭环，全程留痕可查。
- **价值**：知识治理是知识类项目评分权重最高、也最难绕过的交付块。

### R2 消歧确认交互模式（Disambiguation Confirm）— P1 · ≈10–15 人天

现状：`agenticx/runtime/confirm.py` 只覆盖「高风险操作确认」，不支持「多候选选择 / 信息补充」这类消歧语义。

- **能力**：确认协议扩展为三类通用模式——候选选择（返回候选项由用户挑选）、信息补充（提示缺要素）、冲突裁决（语义冲突并列展示）；与 R1 的 NL→规则链路及检索的对象消歧共用同一协议；多轮消歧会话状态由 memory 承载。
- **落点**：`agenticx/runtime/confirm.py` 扩展 + agent_runtime 交互协议。
- **验收**：规则生成与对象检索两条链路均以同一消歧协议处理歧义，无需各自实现。
- **价值**：消歧是人机协同的通用语义，散落在各 agent 实现里各自为政，收敛后同时服务规则、检索、表单填写场景。

### K3 图谱增量更新与审核留痕 — P2 · ≈15 人天（可选）

- **能力**：`agenticx/knowledge/graphers/` 增量同步（按周期或事件，识别受影响对象避免全量重复加工）；抽取 → 审核留痕 → 发布入图的标准链路；与 K2 生命周期联动。
- **落点**：`agenticx/knowledge/graphers/` 扩展。
- **验收**：变更一批源文档后，图谱仅增量更新受影响对象，过程可追溯。

## 不进主干清单（B 层，项目仓承接）

| 项 | 去向 |
|---|---|
| 领域本体实例（资产 / 岗位 / 组织字典）与专业术语词典 | 项目配置仓 |
| 台账 / 工单 / 告警等源系统适配器 | 插件实例（参照 `data_suite/channels` 的通道抽象） |
| 作业知识 / 风险提示 / 案例比对的领域 prompt 包 | Skill / agent 配置层 |
| 客户栈工程适配（Java 微服务壳、等保合规落地、国产化适配） | 交付工程仓 |
| 具体项目的评测集实例 | 评测基准的项目实例 |

## 阶段与节奏

| 阶段 | 内容 | 量级 |
|---|---|---|
| P0 | R1 规则资产与规则引擎 + K1 证据与引用结构 | ≈130–150 人天 |
| P1 | K2 知识生命周期与质量治理 + R2 消歧确认模式 | ≈30–40 人天 |
| P2 | K3 图谱增量更新（视 P0/P1 落地后的项目需求决定是否做） | ≈15 人天 |

合计 ≈175–205 人天。按产品节奏推进，**不绑定任何单一售前项目的交付工期**；每个能力组落地后以需求依据文档的功能域重新跑一次覆盖度测算验证收益（目标：能力域覆盖 49% → 75%~80%）。

## 验收口径（规划级）

1. 上述能力组全部「零引擎改动可配置」接入一个样板项目（YAML / 词典 / 插件即可实例化）；
2. 售前摸底口径的能力域覆盖度复测达到 75% 以上；
3. 效果类评测（规则生成准确率、消歧命中率、引用忠实度）有可复现跑分入口；
4. 主干代码经扫描无任何客户专名、行业专名与可溯源标识（脱敏纪律同 `docs/agx-data-suite/requirement-background.md`）。
