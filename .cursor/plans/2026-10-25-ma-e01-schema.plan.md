## 0. 一句话目标

在 PG / MySQL 双方言下新增 6 张 MA 表与 `enterprise_agents` 的 4 个新列，提供 iam-core 的「Agent 版本（追加写 + CAS）」「Environment CRUD」「会话面只读查询」三组 repo，并把每个现有 `enterprise_agents` 行回填为 version 1（manifest 由现有列构造，hash 用 core-api `manifestHash` 计算）。

## 2. 关键设计决策（本子规划内定，后续子规划不得改）

| # | 决策 | 理由 |
|---|---|---|
| D1 | **回填不在 SQL 迁移里做**，而是 TS：iam-core `ensureAgentVersionOne`（读路径懒回填，事务 + 行锁）+ CLI `pnpm -C enterprise ma:backfill-agent-versions`（`start-dev.sh` / `bootstrap.sh` 迁移后自动跑） | `manifest_hash` 必须与 core-api `manifestHash`（canonical JSON + sha256）逐字一致，SQL 无法复刻 canonical JSON；懒回填保证即使 CLI 没跑，任何读版本的路径也能拿到 v1 |
| D2 | 回填 manifest 的能力映射：`skill:<rowId>` 且在同租户 `enterprise_skills` 中找到 → `skills[]` 一项 `{source:"tenant", id:<rowId>, version:<row.version>}`；`mcp:<rowId>` 与找不到行的 `skill:<rowId>` → 原样放进 `metadata.legacy_capability_ids`（字符串数组，保留原顺序，仅非空时出现）。**不生成 `mcp_servers` / `tools`** | Manifest 的 `mcp_servers[].url` 必填，而托管 MCP 的地址依赖网关对外地址（`/mcp/{name}/streamable-http`），迁移期不可知；硬编码会生成错误 URL。保留原 id 让 MA-E03 / 现有 TS loop 仍能按 id 解析，零信息丢失。skill 有确定的版本来源，所以直接进 `skills[]` 并固化版本（满足 master §5.1「保存后一定有具体版本号」） |
| D3 | 路由存储：`enterprise_agents` 新增 `version_routing varchar(16) not null default 'follow_latest'`（取值 `follow_latest` / `pinned`）与 `pinned_version integer null`；生效版本 = `pinned` 时取 `pinned_version`，否则 `latest_version` | Agent 级默认路由是控制面属性，与 `latest_version` 同一行 CAS；放 `metadata` 会被现有编辑弹窗整包覆盖（admin `agents.tsx` 保存时整体发送 `metadata`）。渠道级路由由 MA-E09 的 `ma_channels` 自己存，不复用此列 |
| D4 | `enterprise_agents` 现有 `model` / `system_prompt` / `capability_ids` 三列定义为**最新版本的投影**：经 `createAgentVersion`（admin/api/desktop 来源）写版本时同一事务内回写投影；经旧 `updateAgent` 改这三列（或 `metadata`）且该 Agent 已有版本行时，同一事务内追加一个 `source='legacy_edit'` 的派生版本 | 现有读者（web-portal 协作房间 TS loop、`/api/desktop/agents`、`/api/me/agents`、Desktop 同步）都读这三列，不能断；同时 master §4.7 要求「每次更新都产生版本」，单一写入方原则下两条写路径必须收敛成「投影 == 最新版本」 |
| D5 | 会话用量：`ma_sessions.usage_totals jsonb`（累计，供详情页直接展示）**加** 独立追加表 `ma_session_usage`（每个 `span.model_request_end` 一行，冗余 tenant/agent/user/model） | master §2.3 已列 `ma_session_usage`；MA-E10 需要按 用户×Agent×日/周/月 聚合，长会话跨天时只有累计值无法切窗，扫 `ma_session_events` JSON 成本过高。列名用 `usage_totals` 而非 `usage`：`USAGE` 是 MySQL 保留字 |
| D6 | `ma_sessions.agent_id` 外键 `ON DELETE RESTRICT`；`enterprise_agent_versions.agent_id` 外键 `ON DELETE CASCADE` | 有托管会话的 Agent 不允许物理删除（会丢版本与审计链），iam-core `deleteAgent` 把 FK 违例映射成 `AgentHasSessionsError`（管理台提示「改为停用」）；无会话的 Agent 删除行为与现在一致（版本随之删除） |
| D7 | 不新增 DB 触发器保证版本不可变；不可变性由 iam-core **不导出任何 update/delete 版本的函数** + 测试保证 | MySQL 迁移文件按 `;` 计语句数（schema-parity 测试 `countTopLevelStatements`），触发器体易误判；应用层单一写入方已足够 |
| D8 | 不改 `EnterpriseAgent` 类型；新增 `EnterpriseAgentMa`（四个新列）与 `EnterpriseAgentWithMa = EnterpriseAgent & EnterpriseAgentMa`，由新函数 `getAgentWithMa` / `listAgentsWithMa` 返回 | web-portal 测试用对象字面量构造 `EnterpriseAgent`，加必填字段会让它们 typecheck 失败（越界改动） |
| D9 | `SYSTEM_PROMPT_MAX` 从 16000 提到 65536 | Manifest `system` 上限 64 KiB（master §5.1）；投影回写后若仍按 16000 校验，管理台「发布 / 回收」（走 `updateAgent` 合并校验）会对长提示词 Agent 报错 |
| D10 | iam-core 新增依赖 `@agenticx/core-api: workspace:*` | 版本写入与回填必须调用同一份 `validateManifest` / `manifestHash`；core-api 无依赖，不会成环 |
