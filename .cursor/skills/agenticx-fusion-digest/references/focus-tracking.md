# 聚焦专题：持续深挖某一类内容

日报负责「广撒网」，聚焦专题负责「深挖」。当用户或战略类智能体（如产品战略助手）判断日报里某一类新内容值得关注、可能要吸收进产品体系时，就为它建一个聚焦专题，之后持续在深度和广度上优先搜集，最终沉淀成一份关于这类内容的全面情报。

聚焦专题建立在定向搜集模式之上：每一轮搜集都按 `targeted-research.md` 的方法检索、分级、核实，区别在于它会持续多轮、跨天累积，并且和日报联动。

## 1. 建立专题

### 谁能发起

- 用户直接说：「日报里那个 X 方向，帮我持续盯一下」「把 X 作为重点情报方向」。
- 战略类智能体通过调用参数发起，内容见下方「专题请求」。

### 专题请求

```json
{
  "topic": "Agent 运行时的沙箱隔离方案",
  "reason": "日报 2026-11-08 出现三篇相关进展，可能影响我们的执行环境设计",
  "seed": [{"digest": "2026-11-08", "urls": ["https://...", "https://..."]}],
  "questions": ["主流方案各用什么隔离技术", "性能和安全的取舍", "有没有可直接集成的开源实现"],
  "keywords": ["sandbox", "microVM", "gVisor", "Firecracker", "沙箱"],
  "requester": "用户 / 产品战略助手",
  "priority": "high",
  "cadence": "daily",
  "product_context": "docs/product/capabilities.md",
  "sinks": ["feishu:<知识库节点>", "local:./intel"]
}
```

| 字段 | 必填 | 缺省时 |
| --- | --- | --- |
| `topic` | 是 | 缺了要问；非交互调用时拒绝建立并返回原因 |
| `reason`、`seed` | 否 | 从对话或最近的日报里补；补不到就留空 |
| `questions` | 否 | 按 `targeted-research.md` 第 2 步自行拆 3–7 个子问题 |
| `keywords` | 否 | 从 `topic`、`seed` 和子问题里提取 8–15 个中英文关键词 |
| `priority` | 否 | `normal`；可选 `high` / `normal` / `low` |
| `cadence` | 否 | `daily`；可选 `daily` / `weekly` |
| `product_context` | 否 | 无。没有时报告里不写「对产品的启示」，只写「值得关注的点」 |
| `sinks` | 否 | 沿用智能体的默认落盘位置 |

### 专题目录

每个专题在状态目录下有自己的目录 `focus/<专题短名>/`：

| 文件 | 内容 |
| --- | --- |
| `focus.md` | 专题定义：主题、发起原因、发起人、子问题、关键词、优先级、频率、状态、建立日期 |
| `inbox.jsonl` | 日报扫到、命中本专题关键词、还没处理的条目 |
| `sources.jsonl`、`notes/` | 与定向搜集相同，跨轮累积 |
| `rounds.md` | 每一轮的日期、做了什么、新增了什么、还缺什么，一轮一段 |

状态取值：`active`（持续搜集）、`paused`（暂停，不搜集也不收件）、`closed`（已结束，保留全部产物）。

建立后立即跑第一轮，深度按「深入」处理，把 `seed` 里的条目作为第一批来源。

## 2. 与日报联动

日报模式第 1 步扫完源后，把每条新条目和所有 `active` 专题的关键词比对：

- 命中的条目写进对应专题的 `inbox.jsonl`，不论它在日报里是否达标。
- 日报打分时，命中 `high` 优先级专题的条目，「决策影响」至少计 1 分。
- 日报正文里写到这类内容时，在章节末尾加一句「已纳入聚焦专题《X》持续跟踪」，不在日报里展开深挖。

## 3. 每一轮怎么做

按 `cadence` 定时运行，或被用户、战略智能体手动触发。每一轮同时做深度和广度两件事：

**深度**：针对还没有可靠答案的子问题继续追。读 `rounds.md` 里上一轮记下的缺口，生成新查询，优先找一手来源：论文、源码、官方技术文档、Issue 讨论。

**广度**：在主题周边找新东西：

- 新出现的玩家、项目、论文，以及 `inbox.jsonl` 里的新条目。
- 相邻方案和替代路线（比如专题是「沙箱隔离」，就看看 WebAssembly 隔离、远程执行服务）。
- 反方证据：失败案例、性能问题、被放弃的项目。

每轮预算按「标准」深度（最多 3 轮检索、20–30 个来源），`high` 优先级可按「深入」。

一轮结束后：

1. 在 `rounds.md` 追加本轮记录。
2. 清空 `inbox.jsonl` 里已处理的条目。
3. 更新累积报告，并写一份本轮增量简报（见下一节）。
4. 连续 3 轮没有新事实时，把频率从 `daily` 降为 `weekly`，并在结果里告诉发起人；`weekly` 也连续 3 轮无新事实时，建议发起人关闭专题。

## 4. 产出

### 累积报告 `report.md`

一份不断更新的完整情报，按 `writing-guide.md`「定向搜集报告」的结构写，另外加三节：

- **全景**：这类内容目前有哪些玩家、方案和路线，用对比表呈现，每格写事实并标取数日期。
- **演进时间线**：关键事件按时间排列，每条一行，带来源编号。
- **对产品的启示**：只在调用方提供了 `product_context` 时写。逐条对照产品现有能力，写出缺口、可借鉴之处和风险。产品现状只依据 `product_context` 的内容，不臆测产品已有或没有某项能力。

报告开头写「最后更新：日期，第 N 轮」。每轮更新时，改动的结论在句末标「（日期 更新）」，被推翻的结论移到「分歧与不确定」并注明原因，不要直接删掉。

### 增量简报 `updates/YYYY-MM-DD.md`

给没空读全文的人看，控制在 500 字以内：本轮新发现（3–5 条判断，带引用）、哪些结论变了、下一轮准备查什么。

### 交给战略智能体

每轮结束返回给发起人的结果包括：专题名、轮次、增量简报全文、累积报告的位置链接，以及需要发起人决定的事（例如「是否要做原型验证」「是否关闭专题」）。

## 5. 结束专题

由用户或发起的战略智能体决定关闭。关闭时：

1. 跑最后一轮，把累积报告定稿，开头写「已结束：日期，原因」。
2. 状态改为 `closed`，从日报的关键词比对中移除。
3. 产物全部保留在落盘位置，不删除。
