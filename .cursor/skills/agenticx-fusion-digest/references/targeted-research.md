# 定向搜集模式

围绕一个明确的问题或主题，多轮检索、交叉核实，产出一份能直接回答问题的研究报告，并附上可追溯的来源记录。

和日报模式的区别：日报是「看看最近出了什么」，从清单出发；定向搜集是「我要弄清楚这件事」，从问题出发，来源不限于清单。需要长期跟踪、反复更新的方向，用 `focus-tracking.md` 的聚焦专题，它的每一轮都按本文件的方法做。

## 1. 明确任务书

开工前把下面几项填齐，写进工作目录的 `brief.md`：

| 项 | 说明 | 没给时的默认 |
| --- | --- | --- |
| 问题 | 要回答什么。一个主问题，必要时附 2–3 个关心点 | 必填，缺了要问 |
| 用途 | 读者拿结果做什么：选型、写方案、竞品对比、了解进展、找人找项目 | 「了解现状并给出判断」 |
| 范围 | 地域、语言、时间范围、要排除的内容 | 中英文来源，最近 12 个月为主，背景可更早 |
| 深度 | 快速 / 标准 / 深入，见下文第 4 步的预算表 | 标准 |
| 指定来源 | 必须查的网站、仓库、本地资料、飞书文档 | 无 |
| 落盘位置 | 本地文件夹、飞书文档或知识库、GitHub 仓库 | 本地文件夹 |

缺「问题」或问题过于宽泛（如「研究一下 AI」）时，用一轮选项式提问收窄，最多问一轮。其余项缺省就用默认值，并在报告的「范围与假设」里写明。

被智能体以非交互方式调用时（参数里已有问题），一律不提问，直接按默认值开工。

## 2. 拆子问题

把主问题拆成 3–7 个子问题，每个子问题都要能单独回答。写进 `brief.md`。

例子：主问题「企业内部部署 Agent 平台，开源方案怎么选」可以拆成：

1. 目前活跃的开源 Agent 平台有哪些，各自定位是什么？
2. 哪些支持私有化部署、多租户和权限控制？
3. 各自的社区活跃度和维护状况如何（提交频率、Issue 响应、发版节奏）？
4. 有哪些公开的企业落地案例或踩坑记录？
5. 许可证对商用有什么限制？

不要拆出「XX 的历史」这类与用途无关的子问题。

## 3. 检索

每个子问题生成 3–6 条查询：中英文各写，换同义词，带上限定词（产品名、年份、`site:` 官方域名、`filetype:pdf`）。

按问题类型选检索渠道：

| 要找的 | 优先渠道 |
| --- | --- |
| 产品能力、定价、发布 | 官方文档、官方博客、更新日志 |
| 技术实现、项目状况 | GitHub 仓库（README、Issue、Release、提交记录）、代码搜索 |
| 研究结论 | 论文原文（arXiv、会议论文）、作者博客 |
| 市场与公司 | 公司公告、财报、可信媒体 |
| 实际使用体验 | 技术社区、论坛、工程博客，只作旁证 |
| 内部资料 | 调用方指定的本地文件夹、飞书文档或知识库 |

### 来源分级

每条来源记录时标一个等级，写报告时决定它能撑多大的结论：

| 等级 | 来源 | 用法 |
| --- | --- | --- |
| A | 一手：官方文档、论文原文、代码仓库、财报和公告 | 可以单独支撑事实 |
| B | 可信二手：专业媒体、知名工程博客、权威评测 | 支撑事实时最好有第二个来源 |
| C | 社区讨论、个人博客、社交媒体 | 只作旁证或线索，不单独支撑结论 |

营销软文、内容农场、无署名无日期的页面不收录。

### 笔记落盘，不堆在上下文里

每读一个有用的来源，立即把要点写进 `notes/` 下的单独文件，同时在 `sources.jsonl` 追加一行：

```json
{"id": 12, "url": "https://...", "title": "...", "publisher": "...", "date": "2026-10-21",
 "accessed": "2026-11-08", "tier": "A", "subq": [2, 3], "note": "notes/012-xxx.md"}
```

笔记文件只写和子问题有关的事实、数字、原文短引（注明段落），以及一行「这条说明了什么」。写完后，原文正文不必留在上下文里。后续综合时读笔记，不重读原文。

## 4. 多轮迭代

每轮检索结束后做一次缺口检查，写进 `brief.md` 末尾的进度表：

- 哪些子问题还没有 A 级来源，或只有一个来源？
- 哪些说法互相矛盾？
- 出现了哪些之前没想到、但和用途相关的新线索？

据此生成下一轮查询。按深度控制预算：

| 深度 | 轮数上限 | 来源数参考 | 适合 |
| --- | --- | --- | --- |
| 快速 | 1 轮 | 8–12 | 先摸个底、回答单一事实问题 |
| 标准 | 3 轮 | 20–30 | 选型、方案调研 |
| 深入 | 5 轮 | 40–60 | 竞品全景、需要对外交付的报告 |

满足任一条件就停：轮数到上限；所有子问题都至少有一个 A 级或两个独立 B 级来源；连续一轮没有带来新事实。

## 5. 核实

报告里每个关键结论都要过一遍：

- 至少一个 A 级来源，或两个互相独立的 B 级来源。同一稿件被多家转载只算一个来源。
- 时效：日期超过范围的，标明「截至某年某月」。产品功能、价格、Star 数这类会变的数字，写上取数日期。
- 冲突：来源说法不一致时不要挑一个写，把分歧列出来，说明你倾向哪边、为什么。
- 找不到：明确写「未找到公开资料」，不要用推测补空。

每个结论标置信度：**高**（A 级来源直接支撑）、**中**（B 级多源一致，或 A 级来源间接支撑）、**低**（只有 C 级来源，或推论）。

## 6. 写报告

结构和写法见 `writing-guide.md` 的「定向搜集报告」部分。要点：

- 第一节就回答主问题，结论先行。
- 每个子问题一节，先判断、再证据，正文用 `[n]` 引用 `sources.jsonl` 的编号。
- 单列「分歧与不确定」「没找到的」两节。
- 配图规则与日报相同，按 `selection-rubric.md` 的四问选图；对比表常常比图更有用。

## 7. 落盘和自检

先过 `SKILL.md` 的通用自检，再加四项：

- [ ] 第一节直接回答了 `brief.md` 里的主问题。
- [ ] 每个子问题都有结论或明确的「未找到」。
- [ ] 每个关键结论有置信度，高置信度的都有 A 级来源。
- [ ] 正文里每个 `[n]` 都能在来源清单里找到，来源清单里每条都有可访问的链接或本地路径。

按 `delivery-sinks.md` 落盘。落盘内容为报告、来源清单，按需附笔记和图片。

## 与已有资料的关系

同一主题之前做过搜集时（落盘位置里有同名或相近主题的报告），先读旧报告的结论和来源清单，本次只补增量，并在报告开头注明「在某日报告基础上更新」。不要从零重做一遍。
