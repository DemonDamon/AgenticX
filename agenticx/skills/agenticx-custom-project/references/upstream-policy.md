# 上游协作约定（操作版）

本文件给新的业务仓库使用。版本是 `v1`。

如果仓库根目录已经有 `<!-- agenticx-upstream-policy:start` 到 `end` 的标记段，以那段原文为准，不要用本文件覆盖它。

业务仓的通用 agent runtime 以 [DemonDamon/AgenticX](https://github.com/DemonDamon/AgenticX) 为能力上游。各仓保留自己的业务边界和发布节奏。接入方式可以是 Git 分叉、SDK 依赖或精简拷贝。本文件不扩大某次任务的发布授权。和上游查阅、贡献有关的冲突，以这九条为准。

## 1. 按改动类型决定要不要查官方，查过的结论要复用

新功能先分开：这是通用内核，还是这家业务的适配。

新增可复用的运行时能力时，必须先做一次有范围的官方核对。同一次开发、同一个模块，已有结论还能用，就直接复用，不要每个子任务都查一遍。

原因已经明确的小缺陷，默认在当前仓库修，并做针对性验证。共享运行时里的小修也一样。可以用你已经知道的官方基线。不要求联网，不要求拉代码，不要求查 Issue 或 PR，也不要求把其他业务仓扫一遍。纯业务文案、样式和客户规则也不查上游。

只有这些情况才重新核对相关模块、测试和标题能对上的 Issue / PR：新增通用能力、核心协议或接口的大改、依赖升级、安全问题、系统性的跨仓问题、准备把改动贡献回去。本地资料不够或基线要更新时，再做定向获取。禁止把「扫全仓、扫全历史、每个 bug 都拉代码、定时同步」当成默认动作。

查过之后，在现有说明里简短记下提交号、路径和结论。没访问最新上游，就不能说已经检查了最新版本。

## 2. 官方已经有的，优先升级或移植

官方已有合适实现时，优先升级依赖、摘取提交，或做最小移植。评估接口、行为和必要依赖是否兼容。只移植需要的能力和它的依赖闭包。

不要为了一个修复去整仓合并、强制同步，或恢复已经裁掉的产品模块。各业务仓不必使用同一个版本。

## 3. 通用改进要能回到官方，但业务不必等

新增的通用能力，以及这一批已经确认的共享内核修复，应拆成官方仓库里能单独复现的最小实现，并带上相关测试。

整理贡献时集中做一次去重：官方已有的按第 2 条处理；还没有的再向官方提 PR，并和本仓改动关联起来。同一问题的相关小修可以按一批处理。不要求每个一行的 bug 都单独联网或新开 PR，也不要把无关功能混进去。

发布按第 9 条的授权执行。确实发不出去时，交出可审查的补丁、PR 正文草稿和具体阻塞，并写明尚未提交。不能用「以后再同步」代替已经完成。

业务修复和交付可以先做，不必等官方审核或合并。

## 4. 业务专属内容留在业务仓

客户流程、采购或审计规则、领域数据、业务界面、部署配置和私有集成留在业务仓。可复用的机制可以抽回官方，不能把整个业务功能搬进运行时。

给官方的复现只用合成数据，或使用已经允许公开的脱敏样例。原始材料、派生结果、内部文档、凭据和运行状态都不能进入公开补丁、提交或 PR。

## 5. 写明真实来源，保留本地差异

和上游有关的变更，在现有的集成说明、依赖声明或提交 / PR 里记录：实际来源仓库和提交、确认过的官方对应提交、必要的适配，以及官方 PR。普通小修不必为了证明流程额外写计划、报告或同步台账。

代码若是从另一个业务仓移植来的，注明那个直接来源，不能改写成「直接复制自官方主仓」。保留原来的许可证、署名和 NOTICE。精简拷贝真正更新之后，维护版本、裁剪范围和本地补丁说明。

## 6. 在集成的时候收口，不要天天轮询

在相关的开发批次、依赖升级或集成时，再跟进已经提交的官方 PR。不要默认开定时轮询。

官方合并之后，按本仓的接入方式升级或移植，并去掉已经被官方覆盖的重复本地补丁。还没对上的适配，写明为什么先留着。

## 7. 确认有影响，再告诉其他仓库

确认某个通用缺陷或能力确实会影响其他业务仓时，再列出适用的仓库、版本或接口条件，以及要同步的改动。在已有授权里关联对应的提交、Issue / PR 和移植结果。

局部 bug 不要默认把每个仓库都扫一遍。没验证、没移植或没发布的仓库必须标明。不能笼统说「所有仓库都已经同步」。

## 8. 按受影响的范围验证

移植或通用实现，要跑受影响的运行时测试，并确认当前业务接入仍然成立。依赖、协议或裁剪范围有变化时，覆盖对应的边界。

验证失败就修原因。不要把结果改成固定值，不要放宽通过条件，也不要用悄悄重试把失败藏起来。

只改文档时，核对内容、链接和 diff。不要为此启动模型、读取凭据或跑全量业务测试。

## 9. 授权和节奏

和任务有关的只读查阅、定向获取，是按需使用的工具，不是每次开发的必经步骤。贡献用的分支、工作区、提交、推送和 PR，按这次任务已经给出的授权执行。已经授权的操作不必反复确认。

官方贡献和业务工作区分开。不要直接推送官方主分支。不要擅自 reset、rebase 或覆盖用户的修改。也不要因为这套约定就自动克隆仓库、改写 remote 或切换业务分支。

权限、网络或发布授权受阻时，只暂停受阻的那一步官方操作。其余已经授权的工作继续做，并把状态说准确。
