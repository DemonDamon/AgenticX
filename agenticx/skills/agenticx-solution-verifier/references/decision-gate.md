# 判据先行与结论分级

验证的价值在于支持决策，而决策需要事先约定「什么算过」。先定通过线再跑实验，是这套方法和「跑一堆实验再挑好看的数字说事」的根本区别。

## 决策问题

写成一句可判真伪的话，并注明决策动作：

| 决策问题示例 | 对应的决策动作 |
|---|---|
| 10 个问题点、每个选 3 张卡时，输入会不会超窗 | 要不要在汇报前做拆分改造 |
| 拆分加条级抽取，关键条款保留率是否不低于 98% | 这个压缩方案能不能上线 |
| 新检索策略在 20 条金标准任务上引用覆盖率是否 100% | 新旧策略切换还是并存 |

## 指标与通过线

- 指标从决策问题拆出来，一般逃不掉这几类：容量（峰值、超窗次数）、质量（保留率、引用覆盖率、一致率）、稳健性（篡改检出率、误报率）、可复现性（两次运行一致性）、性能（时延、吞吐）。
- 通过线从需求、SLA、监管要求或现状反推。写不出来源的要标注「建议值，需对方拍板」。
- 红线指标和质量指标分开：红线（如条款号一致率 100%）任何一项不过就整体不通过，压缩比再好看也不行。
- 每个指标写清口径：统计对象、样本、取整方式。口径不清的数字无法复算，等于没有。

## 禁止事项

- 跑完实验再回头改通过线。
- 只报对结论有利的一档（只报短章、只报均值不报上界）。
- 缓解手段只看峰值不看保留率——截断永远赢峰值，但会丢关键内容。
- 用合成数据的绝对值当性能承诺。

## results.json 规范

每次验证落盘一份，文档和汇报只引用这份文件：

```json
{
  "decision": "这次验证要支持的决策，一句话",
  "env": {
    "model": "真实模型名与量化版本，或 none",
    "context_window": 0,
    "hardware": "硬件与显存/内存",
    "code_ref": "复刻来源 文件:行号"
  },
  "dataset": {
    "source": "synthetic | production | mixed",
    "sample_size": 0,
    "assumptions": "长度分布等人为设定值，逐项列出"
  },
  "metrics": [
    {"name": "", "value": "", "threshold": "", "pass": true, "note": "口径与取整"}
  ],
  "limits": ["边界，逐条"],
  "verdict": "pass | conditional | fail",
  "conditions": ["有条件通过时的条件"]
}
```

## 结论分级

- **通过**：所有红线过、质量指标过、关键结论已过真实环境实测。
- **有条件通过**：算法行为已证，但缺真实数据或真实窗口；条件写成「到现场量哪几个数、补多少条真实样本」，每条可执行、可估时。
- **不通过**：任何红线不过，或主假设被实验推翻。写清阻断项，不要含糊带过。

样本量底线：一般实验每组至少 30 次取均值；检出类每类至少 20 次，干净样本至少 50 次；真实任务回归 20–30 条金标准。达不到的，结论降一级并注明。
