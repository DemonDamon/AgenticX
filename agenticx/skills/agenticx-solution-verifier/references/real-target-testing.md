# 真实环境实测

复刻实验证的是算法行为，实测证的是「在真实模型、真实服务、真实数据上，结论还成不成立」。影响交付的关键结论（能不能上线、方案是否有效）必须过这一关，否则结论最多是「有条件通过」。

## A/B 对照

- 两组：现状一组、方案一组。同一批样本、同一个模型、同一个窗口、同一份 prompt 模板。
- 样本用真实任务最好；拿不到就用合成材料，逐个标注「合成」。
- 记录每组的输入量、实际读入量、输出、命中数。只记录「跑没跑成功」等于没测。

## 必须记录的三样

1. **真实配置**：模型名与量化版本、窗口大小、配置来源（内置默认、配置文件、数据库覆盖）。配置没匹配上模型名时可能有兜底值，要确认实际生效的是哪个。
2. **实际读入量**：推理服务返回的输入统计（如 Ollama 的 `prompt_eval_count`）。输入 2 万 token、实际读入 1 千，说明被截断了，即使返回 200。
3. **输出完整性与内容命中**：输出是不是被思维链或长度上限吃掉；关键条款、关键字段引到几个，逐个对金标准。

## 静默截断识别

超窗不报错是常见实现：服务直接把超出部分截掉，表面成功。识别方法：灌一条已知超过窗口的输入，对比返回的输入统计和实际输入量。一致才说明没截。这个行为取决于现场推理服务的实现，换部署环境要重测一次。

## 与复刻实验互相校准

实测的 token 数和复刻实验的估算值通常有偏差。用真实分词器核对估算函数，算出偏差比例（实例：某项目估算偏高约 14%，100K 真实窗口约相当于 114K 估算值），把容量表的判断阈值折算回去，再逐个核对原来的「超窗/不超」标记要不要改。不要直接用未校准的估算值下结论。

## 资源不足时降级，不硬跑

- 大窗口跑不动（内存不足、换页、进程被杀）就降窗口跑机制验证：超窗截断、压缩前后命中差异，这些机制在小窗口上同样成立，但要在报告里写明窗口差异和折算关系。
- 长任务拆成单点执行，结果逐条写盘。进程被杀时只丢当前这条，不丢整批。
- 硬跑导致数据丢失或结果残缺，比不跑更糟：残缺结果容易被误当证据。

## 接口与思维链的坑

- 同一个模型，raw 生成接口和 chat 接口的模板、默认行为可能不同；关思维链要用服务端支持的显式开关（如 chat 接口的 `think=false`），prompt 里写「不要思考」不可靠。
- 输出被思维链占满时，先换接口或关思维链再判「模型答不出」，不要把接口问题算成方案无效。

## 边界声明

样本小、窗口比现场小、只验了单一指标，都要写进结论。例如「5 个合成样本、2K 窗口、只验条款命中」只能说明方向对，不能证明生成质量；坐实需要 20–30 条真实任务和现场窗口。实测能证什么、不能证什么，写不清楚的实测等于没做。
