# 方案验证器

写代码不是瓶颈，验证才是。一份没有验证过程、没有数据产物的方案，只是参考资料的堆砌，开发完上线必然返工。本技能的产出不是「一份方案文档」，而是「一个由数据支持的决策」：通过、有条件通过、不通过，各自附证据。

适用面不限于某个项目：新模块设计、上下文压缩策略、检索策略、提示词改造、容量规划、性能优化，只要是「要先证明可行再投入」的事，都走这套闭环。

全程守住三条：

- 结论分三类，写的时候分开：**事实**（能指到文件行号或实验记录）、**推断**（写出推理链）、**未知**（直接说不知道，并给出怎么查）。
- 合成数据必须逐个标注，只验证算法行为；影响交付的关键结论必须过真实环境实测这一关。
- 推翻了之前的结论，回复的第一句就讲更正，不要埋在后面。

按下面的顺序走。每一步的命令和模板在 `references/` 里，用到再读。

## 0. 先写下这次验证要支持什么决策

把决策写成一句可判真伪的话：「10 个问题点时会不会超窗」「拆分加条级抽取能不能上线」「这个检索策略比现状准多少」。没有决策问题的验证是浪费时间。决策问题同时决定实验怎么设计、数据要多少、边界怎么声明。

## 1. 判据先行：通过线在跑实验之前定

在跑任何实验之前，先写下指标、每个指标的通过线、结论分级规则。通过线从需求、SLA 或现状反推，不许跑完再凑。结论分三级：通过、有条件通过（条件列清）、不通过（阻断项列清）。

每次验证必须落盘结构化结果 `results.json`：环境、数据来源与样本量、逐项指标对通过线、边界、最终分级。后续所有文档和汇报引用这份文件，不引用记忆。

判据怎么定、结果文件长什么样，见 `references/decision-gate.md`。

## 2. 定位事实源：代码是一手，文档是二手

方案涉及已有系统时，先证明找对了仓库、还原了真实链路：前端入口 → 接口 → 后端函数 → 拼请求的地方。拿业务词在全组织所有分支上搜，三段对不上就不算定位成功。重点找合并点、无上限维度、静默容错。

全新模块没有旧代码可对，就改为确认接口契约和依赖的真实行为，同样要落到文件和行号。

方法见 `references/locate-and-trace.md`。

## 3. 复刻算法，用合成数据做实验

把真实的模板、合并逻辑、估算函数逐行复刻，先自检复刻版和原版结果一致。实验围绕第 0 步的决策设计：容量、缓解、出口校验、可复现性。每个实验至少 30 次取均值；检出类每类至少 20 次、干净样本至少 50 次。长度分布这类设定值要跑三档，不要只报一个数。

方法见 `references/replicate-and-validate.md`。

## 4. 真实环境实测：关键结论必须过这关

用同款真实模型、真实服务或真实数据做 A/B 对照：现状一组、方案一组，同批样本、同样配置。实测要记录真实配置、实际读入量、输出完整性——不报错不等于成功，静默截断要用「实际读入量 vs 输入量」识别。实测结果反过来校准复刻实验的估算偏差。资源不够就降级跑机制验证，写明折算关系，不要硬跑丢数据。样本小就明说只能证方向。

实测方法、踩坑与判读，见 `references/real-target-testing.md`。

## 5. 产出结论，按第 1 步的判据分级

验证报告固定包含：决策问题、判据、数据表、结论分级、边界声明、到现场或上线前还差什么。报告里的每个数字都能回指 `results.json`。

需要把结论写回飞书文档或画板时，用 `references/write-back.md` 和 `scripts/`：每步写入带 revision 锁、失败即停、写完回读校验，不覆盖他人并发修改。

## 6. 回复的顺序

1. 如果推翻了之前的结论，先讲更正。
2. 结论分级和关键数字，给数据文件位置。
3. 哪些数字是建议值或来自合成数据，需要对方拍板或现场确认。
4. 进入开发或上线前，还必须补哪几项验证。
